# 开机自启：方案对比与实施计划

> **最后核对**：2026-11-05 ｜ **状态**：**设计稿，未实施**（本文只做方案对比与实施排期，不改变任何现行行为；现行写法见 [daemon 常驻原理](daemon-常驻原理.md) §6 与 [新手教程](../使用指南/新手教程.md)「第 3 步」）。
>
> 本文解决的问题：**「登录后拉起一次」这件事，有多少种做法、各自代价是什么、我们该走哪条。** 崩溃重拉（后台守护进程）是另一件事，见 [daemon 常驻原理](daemon-常驻原理.md) §2。

## 0. 先分清三件不同的事

「开机自启」这个词常被当成一件事，实际是三层，混在一起就会写出错方案：

| # | 谁负责 | 现在谁在做 | 做错了会怎样 |
|---|---|---|---|
| ① **登录后拉起一次** | 系统触发器（计划任务 / 启动文件夹 / systemd / launchd） | 用户手工配置 | 配错了**静默不起**——没报错、没日志，用户以为好了 |
| ② **崩了重拉** | 后台守护进程（`_watchdog` / pm2 / `run-daemon.ps1`） | 已实现 | — |
| ③ **自己不退** | daemon 的三个 `while(true)` | 已实现 | — |

**本文只谈 ①。** 关键约束：**②③ 已经内置**，所以 ① **不需要**做任何重拉，只需要「拉起一次，且不弹窗」。

## 1. 两条路线、两个缺口

| | 源码开发者 | 发布版用户（`npm i -g @wemind/cli`） |
|---|---|---|
| 有 `scripts/` 吗 | ✅ 有 `run-daemon.ps1` / `run-all-daemons.ps1` | ❌ **没有**（两个包都 `"files": ["dist"]`，见 `packages/wechat-daemon/package.json:19-21`） |
| 现在怎么自启 | Windows 计划任务 → `run-daemon.ps1`（首选）；启动文件夹 + VBS（退路） | 手写 `.bat` 调 `wemind start`（Windows）；手写 systemd unit / launchd plist（Linux/macOS） |
| 主要缺口 | 只在 Windows 有方案；watchdog 逻辑与发布版**重复实现两遍** | 要自己写文件；Windows 会闪窗；PATH 可能找不到 `wemind` |

**两个缺口的根因是同一个**：`scripts/` 不随包发布，于是源码路线自己实现了一套（PowerShell），发布路线只能让用户手工配置。

## 2. 源码开发者方案（Windows）

| # | 方案 | 优点 | 缺点 | 状态 |
|---|---|---|---|---|
| A1 | **计划任务**（登录触发）→ `run-daemon.ps1` | 系统级；`ExecutionTimeLimit=0` 可长期（**默认是 72 小时**，必须显式设 0/PT0S，否则三天后被杀）；无需用户目录写权限 | 需要建任务权限（受管机器常被拒）；`pwsh` 必须全路径（WindowsApps 别名在非交互上下文常解析失败）；**`TaskSettings.Hidden` 不是「隐藏窗口」**——它只表示「不在计划任务列表里显示」 | **现行首选** |
| A2 | **启动文件夹 + VBS** → `run-daemon.ps1` | 零权限；`WScript.Shell.Run(cmd, 0, False)` **真隐藏 + 真脱离** | VBScript 已弃用：**Phase 1**（24H2 起 FOD 预装且默认启用）→ **Phase 2**（约 2027 起 FOD 不再默认启用）→ **Phase 3**（移除所有 VBScript DLL）；用户还得会写 `.vbs` | **现行退路** |
| A3 | 启动文件夹 + `.lnk` 快捷方式 | 零权限；图形界面右键就能建，不用写脚本 | 快捷方式的「运行方式」只有**常规/最大化/最小化**，**没有「隐藏」**——`IShellLink::SetShowCmd` 只接受 `SW_SHOWNORMAL` / `SW_SHOWMAXIMIZED` / `SW_SHOWMINNOACTIVE`，没有 `SW_HIDE`；最小化不等于隐藏 | 未采用 |
| A4 | 启动文件夹 + `.bat` | 最好写 | 直接启动 `.bat`/`.cmd` 时系统**新建控制台窗口**（`Creation of a Console`：`Creating a new console results in a new console window`）→ **会闪一个 cmd 窗口**；要真隐藏得靠 `CREATE_NO_WINDOW` 或 A5 | 未采用 |
| A5 | **PowerShell 直接调 `WScript.Shell` COM**（不落 `.vbs` 文件）<br>`(New-Object -ComObject WScript.Shell).Run(cmd, 0, $false)` | 效果等同 A2 的真隐藏；**不需要 `.vbs` 文件**（放进一个小 `.ps1` 即可）。本机实测可用（`wshom.ocx` 与 CLSID `{72C24DD5-…}` 均在） | 仍依赖 WSH COM 组件。**注意**：被弃用的是 **VBScript 语言**，`WScript.Shell` 是另一个组件——A5 降低了「VBScript 被关」的风险，**没有**降低「WSH 被收紧」的风险 | 未采用（可作 A2 的替代） |
| A6 | 装成 Windows 服务（`sc.exe` / NSSM / WinSW） | 最正规：开机即起（不必登录）、`services.msc` 可见 | 需管理员；**服务在 Session 0 运行，不能与用户桌面交互**；`run-daemon.ps1` 需改造；对一个「个人微信通道」明显过度 | 不推荐 |

### 为什么 A1 是首选、A2 只是退路

计划任务是**系统级**的，不依赖用户目录写权限，能配「不限时长」，且不需要任何脚本语言。VBS 退路存在的唯一理由是：**有些受管机器禁止创建计划任务**（提示「拒绝访问」）。

## 3. 发布版用户方案

**现状**：`wemind start` 是**一次性启动器**（`manage.ts:170` 的 `startDaemon`：先 `stopDaemon(key)` → detached spawn `cli.js _watchdog` → **立刻返回**）。所以自启层只需要「拉起一次」。

| # | 方案 | 优点 | 缺点 | 状态 |
|---|---|---|---|---|
| B1 | 启动文件夹 `.bat` → `wemind start` | 一行搞定、零权限 | ① **闪 cmd 窗口**；② `wemind` 靠 npm 全局 bin，**登录时的 PATH 未必有它**（fnm / nvm / Volta 尤其）；③ 仍要用户手写文件 | **现行唯一** |
| B2 | 计划任务 → `wemind start` | 无窗口、系统级 | 同 A1 的权限问题；`wemind start` 本身已 detached，计划任务只当触发器，收益有限 | 未采用 |
| B3 | **`wemind service install`**（项目自实现） | **一条命令跨三平台**；正确处理平台差异（Windows 用 `wemind start`、Linux/macOS 用 `wemind daemon`）；用户零手工 | 要写代码 + 三平台实测 | **未实施**（见 §5） |
| B4 | npm `postinstall` 自动装自启 | 装完即自启 | **强烈不建议**：全局包无提示改系统状态、卸载不清理、CI / 容器环境会炸 | 否决 |
| B5 | 交给 pm2（`wemind start --runner pm2` + `pm2 startup`） | 已实现、跨平台 | 多装一个 pm2；Windows 上 `pm2 startup` 弱（还得计划任务） | 已有，非自启专用 |
| B6 | 只给文档、不自动化 | 零成本 | 用户要自己查平台差异；写错**静默失败** | 现状 |

## 4. 多账号：现在为什么繁琐

### 4.1 事实（源码核实）

| 事实 | 出处 |
|---|---|
| `wemind start` **只启动一个账号** | `cmdStart(sel?)` → `pickKey(sel)` → `startDaemon(key)`（`manage.ts:390-394`） |
| 省略账号 = **默认账号**（不是「全部账号」） | `pickKey()`：`getDefaultKey()`（`cli-context.ts:59-64`） |
| 默认账号缺失时**回落「第一个登记的账号」** | `getDefaultKey()`（`accounts.ts:96-101`） |
| 首个登记账号**自动成为默认** | `if (!reg.default) reg.default = meta.key`（`accounts.ts:128`） |
| 账号由**参数**决定，不是继承环境 | `watchdogStart()` 用 `WECHAT_ACCOUNT: key` **覆盖**父进程环境（`watchdog-runner.ts:148-155`） |
| **`WECHAT_DATA_DIR` 优先于 `WECHAT_ACCOUNT`** | `DATA_DIR = process.env.WECHAT_DATA_DIR?.trim() \|\| path.join(WEMIND_ROOT, ACCOUNT_KEY)`（`account.ts:14-15`） |

### 4.2 于是有两个坑

**坑 1 · 静默指向错误的账号。** 先登录 A（自动成为默认）→ 后来才登录 B → 自启脚本写 `wemind start` → **每次开机拉起的是 A，B 永远不自启**，且**没有任何报错**（`wemind list` 里 A 显示运行中）。

**坑 2 · 残留的 `WECHAT_DATA_DIR` 会压过账号参数。** 自启环境里若残留该变量（例如用户按《速查》配过自定义数据目录并写进了计划任务环境），即使 `wemind start 我的号` 传了正确 key，daemon 仍去读那个显式目录。`run-all-daemons.ps1` 已专门把它从子进程环境移除（第 38 行），`wemind start --all` 必须照做。**这是现行 `wemind start` 的既有缺陷**（会静默空转 / 起错账号 / 停不掉），结论与修法见 [待办：`wemind start` 与 `WECHAT_DATA_DIR`](../待办与后续计划/待办-start-与-WECHAT_DATA_DIR.md)——修法与 P1 共用同一个 `launcherEnv`，建议一次提交。

### 4.3 期望的行为（用户视角）

> 登录了几个微信账号就自启几个；登出了就不再自启。**用户不该手写 N 条。**

### 4.4 方案对比

| # | 方案 | 优点 | 缺点 |
|---|---|---|---|
| M1 | **`wemind start --all`**（新增开关） | 显式；**不破坏现有语义**（无参仍是「默认账号」）；开机读 `accounts.json` → 登录即自启、登出即消失，**账号增减零维护** | 新增开关 + 测试 |
| M2 | `wemind start` 无参改成「全部账号」 | 命令最短 | **破坏性**：现在无参 = 默认账号，改了会让「只想起一个」的人静默起全部；与 `stop`/`session`/`task` 的「省略 = 默认账号」口径不一致 |
| M3 | 自启条目直接调 `wemind start --all` | 一行配置管所有账号 | 依赖 M1 |
| M4 | 监听 `accounts.json` 变化实时起停 | 登录后立刻自启，不必等下次开机 | 过度设计：多一个常驻 watcher、跨平台文件监听不可靠；而登录时的 `--start` 已能覆盖首次 |
| M5 | 维持现状（只有源码版有 `run-all-daemons.ps1`） | 零改动 | 发布版用户仍要手写 N 条 |

**推荐 M1 + M3。**

```powershell
wemind start --all          # 遍历注册表，每个账号各起一个 _watchdog
```

语义要求（写进实现与测试）：

- 每个账号仍是**独立的** `_watchdog` + 独立数据目录 + 独立单实例守卫（复用现有机制，不改并发模型）；
- 某个账号起不来 → **报出该账号、继续起其余**，最后汇总（不要因为一个坏账号让整批失败）；
- 登出 / 删除账号 → 注册表里没了 → 下次开机自然不再拉起；
- 起之前**移除继承的 `WECHAT_DATA_DIR`**（见坑 2）。

## 5. `wemind service install`（建议的统一接口）

### 5.1 要解决的

用户侧**只需要记一条命令**，不用知道三平台差异：

```powershell
wemind service install            # 为默认账号安装自启
wemind service install --all      # 为所有已登记账号安装（模板化）
wemind service status             # 看装了没有、跑没跑
wemind service uninstall          # 卸载
```

### 5.2 各平台生成什么

| 平台 | 生成物 | 主进程 | 为什么 |
|---|---|---|---|
| Windows | 计划任务（登录触发、`ExecutionTimeLimit=0`）→ `wemind start --all` | detached `_watchdog` | Windows 的计划任务**只负责拉起一次**，不做重拉；重拉交给内置 `_watchdog`。**不要指望 `TaskSettings.Hidden` 隐藏窗口**——它只影响任务是否出现在列表里；窗口不可见靠程序自身的 `windowsHide` / `WScript.Shell.Run(…, 0, …)` |
| Linux | `wemind@.service` 模板 + `systemctl --user enable --now` + 提示 `loginctl enable-linger` | **`wemind daemon`**（前台常驻） | systemd **本身就是 supervisor**，自带 `Restart=always` |
| macOS | 每账号一个 LaunchAgent plist（`RunAtLoad` + `KeepAlive`） | **`wemind daemon`**（前台常驻） | launchd **本身就是 supervisor** |

**为什么 Linux/macOS 不能用 `wemind start`**（两条都来自官方文档核实，比现有文档写的「会反复重启」更硬）：

1. `wemind start` 拉起后台守护进程后**立刻退出** → systemd / launchd 判「服务已退出」→ 重拉 → 无限循环；
2. **systemd 默认 `KillMode=control-group`**：主进程（`ExecStart` 那个）退出时，**整个 cgroup 的进程都被杀掉**——包括 `wemind start` 用 `detached` 摘出去的 `_watchdog`。所以这不是「能跑但不好」，是**跑不起来**。

### 5.3 统一源码路线与发布路线（重要）

**要统一的是「接口」，不是「机制」。** 强行让三平台跑同一个 supervisor 是跟平台对着干；真正该收掉的是**同一套语义被实现两遍**：

| 语义 | `run-daemon.ps1`（源码版） | `_watchdog`（发布版） |
|---|---|---|
| 崩溃重拉 | PowerShell `while` 循环 | Node `for(;;)` |
| 单实例守卫 | 命名 Mutex | `wrapper.pid` + 身份校验 |
| 日志轮转 | 脚本内 PS 函数 | `RotatingLog` |
| 平台 | Windows only | 跨平台 |

任何一处修 bug 都得改两遍——这才是「维护几套」的真实成本。

| # | 方案 | 优点 | 缺点 |
|---|---|---|---|
| U1 | **`run-daemon.ps1` 降级成薄壳**：只负责「定位 node 绝对路径（保留 fnm/nvm/Volta 兜底）+ 仓库根」，然后 `node dist/cli.js start <key>` | **只剩一份 watchdog 实现**；源码开发者跑的**就是发布版那条代码路径** → 能提前发现问题 | 需改脚本 + 文档；源码开发者不再「完全不经过 CLI」——但现状本来也是跑 `dist/cli.js`，影响很小 |
| U2 | POSIX 也用 `_watchdog`（`ExecStart=wemind _watchdog`） | 三平台同一进程模型 | 在 systemd/launchd 底下再套一层 watchdog，是「包装的包装」；丢掉 journald / `systemctl status` 的原生体验 |
| U3 | 维持三套外壳 | 零成本 | 「维护几套」的痛点原样保留 |
| U4 | **`service install` 统一「安装接口」**，底层仍用各平台原生 supervisor | 用户侧一条命令跨三平台；**同一个生成器被源码路线和发布路线各测一遍** | 要写代码；底层机制仍不同（但这正是平台该有的样子） |

**推荐 U1 + U4**：

- **U1** 收掉「watchdog 实现两遍」这个真正的重复；
- **U4** 让**用户看到的**统一成一条命令，而「不统一」的地方（Windows 用 watchdog、POSIX 用系统 supervisor）恰好是每个平台本来就该这样。

## 8. 待实测清单

- [x] Windows：计划任务勾选「不管用户是否登录都要运行」时，任务**在非交互桌面运行**（`TASK_LOGON_S4U` 原文「non-interactive desktop」），且服务宿主在 Session 0（本机实测 `Schedule` 的 svchost `SessionId=0`）。**推论**：该任务里的程序**不能与用户桌面交互**——微软没有逐字写「计划任务在 Session 0」，这是两条一手结论的推论（2026-11-05 核实）
- [x] Windows：`ExecutionTimeLimit` 默认 **PT72H**（本机 `NewTask(0)` 读回 `PT72H`），必须显式设 `0`/`PT0S`（2026-11-05 核实）
- [x] Windows：`.lnk` 的 `ShowCommand` 只接受 1/3/7，设 0 读回变 1 → **快捷方式无法表达「隐藏」**（本机实测 + `IShellLink::SetShowCmd` 文档，2026-11-05 核实）
- [ ] Windows：`.lnk` 的「最小化」是否会在登录瞬间**可见**（本机测到 `MainWindowHandle≠0`，说明最小化窗口真实存在，但不等于用户看见；待真机登录观测）
- [x] VBScript 三阶段：Phase 1（24H2 起 FOD 预装、默认启用）→ Phase 2（**约 2027** 起不再默认启用）→ Phase 3（移除全部 VBScript DLL，无日期）。`WScript.Shell`（`wshom.ocx`）与 `vbscript.dll` 是**两个不同文件**（2026-11-05 核实）
- [x] Linux：systemd `KillMode=control-group` 杀 cgroup（`systemd.kill(5)` 原文 + 默认值，2026-11-05 文档核实；**未真机验证**）
