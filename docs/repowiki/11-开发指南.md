## 11.1 环境要求

- Node.js >= 20.19（发布包 `engines` 的下限；CI 的 `min-node` 任务在 Node 20 上跑测试，主任务在 Node 22 上跑全量，已在 Node 24 实测；**Bun 未单独实测**）。**从源码构建**需要 Node >= 22.18：`tsdown` 的 `engines` 是 `^22.18.0 || >=24.11.0`，`min-node` 任务因此只构建 core（tsc）并跑测试，不跑 `npm run build`。
- npm（项目用 npm workspaces）。
- 若要跑 daemon 形态：需要一个 ACP agent CLI 在 PATH 上（如 `kiro-cli` / `opencode` / 桌面端 `dsh`；未配置时默认 `auto` 探测已安装者，用 `wemind brain set <agent 名>` 写入磁盘指定）。**起子进程统一用 `spawnAgent()`**，不要自己写 `spawn(bin, args, { shell: true })`——Windows 的 `.cmd`/`.bat` 由它内部经 shell 处理，直接开 shell 会触发 Node 的 DEP0190 警告并放大参数注入面（详见 [AGENTS.md §4.6](../../AGENTS.md)）。

## 11.2 本地开发

```bash
git clone <repo>
cd WeMind
npm install           # 安装所有 workspace 依赖

npm run build         # 按 @wemind/wechat-ilink-core → @wemind/cli / @wemind/wechat-mcp 顺序构建
npm start             # 运行 MCP server（node packages/wechat-mcp/dist/index.js）
npm run daemon        # 运行 daemon（需先扫码登录）
npm test              # 运行单元测试（vitest）
npm run typecheck     # 仅类型检查

# 热重载开发 MCP server（可选）
npm run dev -w @wemind/wechat-mcp
```

## 11.3 构建顺序与产物

构建有**严格的依赖顺序**：core 必须先构建（daemon 直接引用其 `dist`，@wemind/wechat-mcp 内联其源码）。根 `package.json` 的 `build` 脚本保证了这一点：

```jsonc
"build": "npm run build -w @wemind/wechat-ilink-core && npm run build -w @wemind/cli -w @wemind/wechat-mcp"
```

| 包                  | 构建工具 | 产物                                  | 说明                  |
| ------------------- | -------- | ------------------------------------- | --------------------- |
| `wechat-ilink-core` | `tsc`    | `dist/`（含 `.d.ts`）                 | 被另两个包消费        |
| `@wemind/cli`（源码目录 `wechat-daemon`） | `tsdown` | `dist/cli.js` + `dist/cli.js.map`（单文件，内联 core） | 发布产物，命令 `wemind` |
| `wechat-mcp`        | `tsdown` | `dist/index.js`（单文件）             | 内联 core，是发布产物 |

入口路径：

- MCP server：`packages/wechat-mcp/dist/index.js`（bin: `wemind-mcp`）；
- daemon：`packages/wechat-daemon/dist/cli.js daemon`（安装后即 `wemind daemon`）；
- 管理 CLI（与 daemon 同一入口）：`wemind`（产物 `packages/wechat-daemon/dist/cli.js`）。

> **两个包都已发布**（`@wemind/cli`、`@wemind/wechat-mcp`）。发版流程：`npm run check:version` → `npm run build` → 推 `main` 由 CI 发布；手册（含一致性约束与首次发布留档）见 [`docs/发布与变更记录/如何发布新版本.md`](../发布与变更记录/如何发布新版本.md)。`npm publish` **不会**自动 build。

## 11.4 TypeScript 配置

共享配置 `tsconfig.base.json`：target ES2022、module/moduleResolution NodeNext、`strict: true`、`declaration: true`、`esModuleInterop`、`resolveJsonModule`。各包的 `tsconfig.json` 继承它。

> **TypeScript 7.0（原生编译器）注意**：原生编译器不再像旧版那样自动把 `node_modules/@types` 全部纳入编译，因此各包 `tsconfig.json` 显式声明了 `typeRoots`（指向根 `../../node_modules/@types`）与 `types`（core 为 `["node"]`，daemon/mcp 含 `"qrcode"`）。漏掉会报 `TS2591 Cannot find name 'process'/'Buffer'` 一类错误。

全项目是 ESM（`"type": "module"`），import 路径带 `.js` 后缀（NodeNext 要求）。

写新测试时：放在同目录 `*.test.ts`，遵循「纯逻辑 + 依赖注入 mock 外部副作用」的模式；碰用户目录的一律用 `mkdtempSync` 临时目录并**显式传 `dir` 参数**（`DATA_DIR`、`WEMIND_MAX_WORKERS` 这类模块加载期常量要在 import 前设好）。需要走真协议路径时用 **「假 ACP agent」**——写到临时目录的 node 脚本，以 `{bin: process.execPath, args: [script]}` 注入；`brain-switch.test.ts`（切换/回滚/等在途回合结束）与 `pool-spawn.test.ts`（复用/回收）就是这么做的，这是本地验协议路径的标准做法。

## 11.6 持续集成与发布（CI）

`.github/workflows/ci.yml`：在 push（`main`/`feat/**`/`fix/**`）与 PR 时，于 **ubuntu + windows 两个平台**（Node 22）跑完整流水线；另有 `min-node` 任务在 **ubuntu + Node 20** 上只构建 core 并跑测试（验证发布包声明的最低版本；`tsdown` 不能在 Node 20 上跑）：

```
npm ci → npm run lint → npm run format:check → node scripts/check-agent-docs.mjs → node scripts/gen-docs-tables.mjs --check
→ node scripts/doc-impact.mjs --check → scripts/check-docs.ps1 → npm run typecheck → npm run build
→ npm run check:version → npm pack --dry-run -w @wemind/cli -w @wemind/wechat-mcp → npm test
```
`npm pack --dry-run` 会触发两个包的 `prepack` 守卫（文件齐全、bin 存在且带 shebang、sourcemap 随包），版本或打包回归在 CI 就暴露，不必等到发布工作流。

提交前本地跑 `npm run verify`（与上面 CI 同口径，另含 `check-docs.ps1`）可避免 CI 失败。`npm install` 的 `prepare` 会把 `core.hooksPath` 指到仓库的 `.githooks/`，pre-commit 在提交前跑 `format:check`、`doc-impact --check --staged` 与 `check-agent-docs`——漏跑 `npm run format` 或漏同步文档时问题留在本地，不会推到 Actions。

### 文档守卫（三个只读脚本）

| 脚本 | 检查什么 | 失败时怎么办 |
| --- | --- | --- |
| `scripts/doc-impact.mjs` | 本次 diff 触发「改代码 → 必须同步哪些文档」的哪条规则（12 条，规则表在 `scripts/doc-impact.rules.mjs`），以及这些文档是否也在本次改动里 | 按输出清单同步文档；纯重构 / 只改注释 / 只改测试可写 `Docs-Impact: none — <理由>` 豁免（pre-commit 没有提交信息，用 `DOCS_IMPACT` 环境变量，值只写 `none — Pure refactor` 即可） |
| `scripts/check-agent-docs.mjs` | `agents/brain-presets.ts` 里 `ACP_AGENT_PRESETS` 的每个预设是否有接入文档，且含头部三字段、五类小节、独立 `## 待实测`、四处索引 | 按输出补齐；没有待测项就在 `## 待实测` 下写「无」 |
| `scripts/gen-docs-tables.mjs --check` | 环境变量表 / 预设表 / CLI 命令表的标记块是否与代码一致（指令表读 `ipc/chat-command-specs.ts`） | 跑 `npm run docs:tables` 重新生成后一起提交 |

三者都在 `npm run verify` 与 CI 里；前两个也在 pre-commit（`doc-impact` 带 `--staged`，只看暂存区）。脚本自身的用例在 `scripts/doc-guards.test.mjs`。设计说明见 [`文档守卫设计.md`](../设计文档/文档守卫设计.md)。

**发布工作流**（push `main` 触发，也可手动 `workflow_dispatch`）：

| 工作流 | 发布对象 | 触发路径 |
| --- | --- | --- |
| `wechat-mcp-publish.yml` | `@wemind/wechat-mcp` | `packages/wechat-mcp/**`、core、根配置 |
| `wemind-publish.yml` | `@wemind/cli`（命令 `wemind`） | `packages/wechat-daemon/**`、core、`scripts/prepack-guard.mjs`、`scripts/check-version.mjs`、根配置 |

两者都用 npm **Trusted Publishing**（`id-token: write`，无长期 token，带 provenance），并在发布前加两道专属关卡：

1. `npm run check:version`：包名 `@wemind/cli`、`bin` 含 `wemind`，且 `package-lock.json` 的版本与 `package.json` 同步；同时断言 `src/shared/version.ts` **没有**回退成硬编码的 `CLI_VERSION` 字面量（版本号唯一来源是 `package.json`）。MCP 工作流用等价的内联校验；
2. `prepack` 守卫（`scripts/prepack-guard.mjs`，**两个包都配了**）：`files` 目录非空、`bin` 存在且带 shebang、声明了 sourcemap 就必须把 `.map` 带进包；
3. 两个工作流都会把 tarball **真装到临时目录**再决定是否发布：CLI 跑 `wemind version` / `help`，MCP 用临时 `WECHAT_DATA_DIR` 走一次 `initialize` 握手并检查 `serverInfo.name=wemind`。

版本已存在时只跑检查并跳过发布（`::notice::`），不会失败。完整发版手册见 [`docs/发布与变更记录/如何发布新版本.md`](../发布与变更记录/如何发布新版本.md)。

## 11.7 代码约定与风格

从源码可观察到的约定：

- **注释为「为什么」服务**：源码注释解释设计取舍、踩过的坑、关键约束（大量 `[实测]` 标注真机验证结论），而非复述代码。
- **防御性 I/O**：**关键状态**用原子写（临时文件 + rename）——凭证/账号注册表/白名单、`brain.json`、会话表与登记表、`tasks.json`、`task-state.json`、挂起队列等（`store/account.ts`、`atomic-json.ts` 及各模块的 `tmp-*` 写法）。**并非所有 JSON 都原子写**：pid 文件（`daemon.pid` / `brain.pid` / `wrapper.pid`）、控制桥 `.bridge` 凭据、两个沙箱的 MCP/设置镜像（`mcp-sandbox.ts`）、`ecosystem.config.cjs` 生成（`pm2-runner.ts`）都是裸 `fs.writeFileSync`——这些要么是可重建的派生文件、要么只由单一方写入，丢半截不会毁数据。改这些地方时想清楚「写坏了会怎样」，别照抄原子写。读取坏文件不静默清空，而是备份 + 记日志。
- **错误分类正交**：业务错误码（`error-codes.ts`）与传输层错误（`transport-errors.ts`）分离。
- **依赖单向**：消费方只依赖 core，彼此不耦合；core 不依赖任何消费方。
- **配置优先 env**：可调项几乎都通过环境变量暴露，默认值合理，改配置不动代码。
- **Lint / 格式化**：`oxlint`（`correctness` 类规则，CI 上 error）+ `oxfmt`（未配置项、走默认 `printWidth: 100`）统一把关；本地 `npm run lint` / `npm run format`，CI 跑 `lint` 与 `format:check`。提交前用 `npm run verify` 一次跑齐；pre-commit 钩子还会兜底检查格式。
- **借鉴来源标注**：借鉴自 openclaw-weixin / wxclawbot-cli 等的实现都在注释与 CHANGELOG 注明（均 MIT）。

## 11.9 调试技巧

- **看日志**：daemon 所有日志写 `~/.wemind/<key>/daemon.log`，前缀区分子系统（daemon 统一前缀 `[wemind/wechat-daemon]`）：`[wemind/wechat-daemon]`（主循环/发送）、`…/acp`（对话大脑）、`…/worker`（任务 worker）、`…/task`（任务状态机）、`…/watchdog`、`…/wrapper`（后台守护进程）；内核侧 `[wemind/wechat-ilink-core]` 及其 `/ilink`（上下线通知）、`/store`、`/accounts`、`/allow-from`（持久化）子前缀。`tools/messages.ts` 里给客户端渲染用的 `[Image]`/`[Voice]`/`[File]`/`[Video]` 是**内容标签**（消息正文的一部分），不是日志前缀，故意保留。
- **验证 agent 解析**：`node packages/wechat-daemon/dist/cli.js brain`（或安装后的 `wemind brain`）看「生效」行；daemon 包是单文件打包（`dist/cli.js`），没有 `dist/brain-agents.js` 这类模块可单独 import。
- **关键日志线索**：`[wemind/wechat-daemon/acp] spawn ... → initialized → session/new|load → session/prompt → prompt ok` 表示一轮成功；`prompt FAIL ... -> rebuild` 表示大脑超时自愈。
