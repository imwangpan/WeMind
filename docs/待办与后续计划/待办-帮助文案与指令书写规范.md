## 1. 问题

`帮助`（微信）与 `wemind help`（CLI）共用同一张表。当前微信侧实测输出：**24 条 / 1427 字 / 30 行**，条目之间无空行，而微信会把连续空行压成一行——最终是一整块文字墙。

四个具体毛病：

1. **没有主次**：`新会话`、`任务列表` 这种天天用的，与 `重置工作区`、`微信配置 查看` 平级。
2. **一行塞两种写法**：`新会话 [名字] ｜ /new [名字] — 清空上下文重开（可命名）`，手机上折两行还带个 `｜`。
3. **说明里套括号从句**：`重命名会话 … — 给会话起名字（命名后不会被淘汰；旧名字带空格时用引号括起来）`。
4. **术语直出**：`agent`、`overlay`、`brain.json`、`managed/direct`、`进程留着复用`、`收件人`。

再往下一层，是**没有统一的书写规范**——同样是「必填参数」，四种写法并存：

| 现状写法 | 出现位置 |
| --- | --- |
| `<编号>` | `#<编号> 正文` |
| `<序号\|名字\|id前缀>` | `恢复会话 …` |
| `<agent 名>` | `任务 <agent 名>：正文` |
| `编号`（裸写） | `结束任务 [编号]` 的说明里 |
| `[编号]` | `结束任务 [编号]` 的主名 |

斜杠写法有时用 `｜`、有时用 `、`；说明里的人称时中时英。这些直接影响“能不能照着发”，但都没有成文规则。

## 2. 待办 A：帮助信息改造（方案 1+2+3 组合）

已定方向（2026-11-19 与用户确认，**先不改**）：

- **A1 默认视图**：只给 6 条高频指令（`新会话` / `任务` / `#编号 正文` / `#编号` / `任务列表` / `结束任务`），每条一行，用真实例子不用占位符；末尾一行指向分主题与全部。
- **A2 分主题**：`帮助 任务` / `帮助 会话` / `帮助 大脑` / `帮助 其它`，只出对应分区。
- **A3 全部视图**：`帮助 全部` 出完整 24 条，用**两列 markdown 表格**（`| 发什么 | 做什么 |`）——微信能渲染表格且可左右滑动（2026-11-18 实测），CLI 侧不能打 markdown，改用已有的对齐表格（`tasks/task-table.ts` 的 `renderTaskTable()`）或一行一条。
- **A4 文案规则**：动词开头、一条只说一件事、括号补充要么删要么另起一行、术语换人话、英文名词首次出现给中文解释。
- **A5 连带要改**：`renderHelp()` 增加参数解析（`帮助 [分区|全部]`）、24 条 `brief` 全部重写、`wemind help` 复用同一套文案、`README.md` 的 `cli-commands` 自动表重生成、`chat-commands.test.ts` 的 `toContain` 断言（**断言里的句子就是验收标准**）。

### A7 验收

- 默认视图 ≤ 12 行、≤ 500 字；每个分区 ≤ 8 行。
- 24 条都有**可照抄的真实例子**，不再出现 `<占位符>`，因此那句「`<尖括号>` 表示占位内容」可删。
- 真机确认：微信里表格能渲染、长行不会折得难看、`·` 与 `【】` 在不同机型上都还在。
- `npm run verify` 全绿（含 `check-user-copy`）。

## 3. 待办 B：全项目指令与提示的书写规范（逐条讨论后成文）

这项影响面比 A 大：所有微信回执、错误提示、CLI 帮助、README 命令表、`brief`、进度提示。**先讨论，不预设结论**。

| # | 问题 | 现状 | 候选 |
| --- | --- | --- | --- |
| B1 | 必填参数用什么包 | `<编号>` 与裸写 `编号` 并存 | `<编号>` / `编号` / `〈编号〉`（全角） |
| B2 | 可选参数用什么包 | `[编号]` | `[编号]` / `（可选）编号` / `编号?`（注意与 markdown 链接语法 `[文字](url)` 视觉冲突） |
| B3 | 「多选一」怎么写 | `<序号\|名字\|id前缀>` | `<编号 / 名字>` / 拆成多行例子 / 只给一个最常见的 |
| B4 | 占位符 vs 真实例子 | 帮助全用占位符，报错全用实参 | 帮助用例子（推荐）、报错用占位符 + 例子 |
| B5 | 尖括号本身在微信里是否安全 | 未实测 | 需真机验证 `<` 会不会被吞或转义 |
| B6 | 斜杠等价写法怎么呈现 | `中文 ｜ /slash` 同行 | 只在一处列 / 分区末尾统一列 / CLI 不显示斜杠 |
| B7 | 引号约定 | 说明里用「」、参数里用 `"…"` | 统一：参数用半角 `"`，正文引用用「」 |
| B8 | 术语与中英混排 | `agent` / `MCP` / worker / brain 混用 | 用户可见处统一「工作机 / 大脑 / 插件」；英文只在技术文档出现 |
| B9 | 错误/回执的结构 | 有的「结论+原因+下一步」，有的只有结论 | 统一三段式；只读结论时也留「下一步怎么自救」 |
| B10 | 标点与符号 | 顿号当「或」用过（已修一次）、emoji 随意 | 可选动作用「或」不用顿号；emoji 只在分区标题与状态用；全角括号统一 |
| B11 | 数字/时间/大小单位 | `180s` 与 `3 分钟`并存、`523B` 与 `511 KB` 并存 | 期限类用中文（3 分钟），日志/诊断用秒；文件大小统一 KB/MB |
| B12 | 行宽 | 最长一条 40+ 字 | 单行 ≤ 24 字（手机一行内） |
| B13 | 怎么防回退 | 只有 `check-user-copy` 的禁用词表 | 扩展守卫：参数包裹符号、行宽、禁用词、emoji 白名单；再配 `AGENTS.md` 一条硬约束 |

## 4. 落地顺序（建议）

1. **先定 B1–B4**（参数包裹与占位符），因为它直接决定 A 的样张长什么样。
2. 改 **A**（帮助信息），一次性把 24 条 `brief` 按新规范重写。
3. 把 B 的结论落成三处：`docs/ai/术语表.md`（术语对照）、`AGENTS.md` 一条硬约束、`scripts/check-user-copy.mjs` 的结构化检查（能机器判的才写进去，判不了的靠评审）。

## 5. 不做什么

- 不因为是“文案”就顺手改命令名与语义——本次只改呈现。
- 不给 CLI 引入 `--flag` 之外的新参数风格（那是 POSIX 习惯，不改）。
- 不做多语言。
