# 待办：WeMind 自带管理 MCP（admin MCP）

> **状态**：暂缓（2026-11-14 记录，当前先不做）｜ **适用范围**：现行代码（`packages/wechat-daemon/src`）+ 未来扩展
> **触发原因**：《WeMind 接入 Agent 工作模式设计与实现》§7.6.1 原计划的 `wechat_config` / `agent_config` 被判定为当前需求下的过度设计——默认 `direct` 下「让 Agent 自己改配置」就够。但这个想法本身有独立价值，单独记录下来供后续扩展。
> **当前结论**：**本轮不做**。本文只记录概念、玩法与前置条件，不构成实施承诺。

---

## 1. 它是什么

一个**由 WeMind 自己实现、运行在本机的 MCP server**：把 WeMind 自身的能力（配置、会话、任务、工作区、观测）暴露成 MCP 工具，供 Agent 或任意 MCP 客户端调用。

两个使用形态：

| 形态 | 谁在调用 | 怎么接进来 |
|---|---|---|
| A. 会话内 | 微信侧 brain / worker 的模型 | WeMind 把该 server 作为一个 stdio `mcpServers` 项注入会话（仅对接受 ACP `mcpServers` 的 Agent），或写进 Agent 配置 |
| B. 独立 | Claude Desktop / Cursor 等外部 MCP 客户端 | 与 `wemind-mcp` 平级，作为第二个 bin 发布 |

**决定成本的关键事实**：ACP 没有「宿主向模型注册工具」的标准方法。所以形态 A 也必须落成一个真实的本地 MCP server 进程，再经 `mcpServers` 交给 Agent，而不能在 ACP 连接层直接塞工具进去。

---

## 2. 为什么不现在做

- **需求上不需要**：默认 `direct` 下「把模型改成 X」「加载某个 MCP」直接把消息交给 Agent 侧模型即可，不需要 WeMind 再造一个受控写入口。
- **前置缺失**：写配置需要「校验 → 备份 → 并发校验 → 原子写 → 触发 idle reload」。这套逻辑目前散在 CLI（`cli-config.ts` / `agent-config-writer.ts`）里，要先抽成内部配置服务，CLI 与 MCP 共用，否则会出现两套写入路径。
- **回环与 yolo 风险**：工具一旦可写，就要和「WeMind 自己下发的 MCP 集永久排除 `wechat`」这条硬约束、以及控制桥「只接受 agent 名 + 纯数据，没有 `bin`/`args`/`shell`」的契约对齐；yolo 下模型误改配置没有二次确认。
- **容易长成「替用户修 Agent」**：这正是当前刻意避免的耦合方向（Agent 侧的模型/供应商/登录问题属于 Agent 自己）。

---

## 3. 可能的玩法（收藏夹）

按读 / 写分档；写操作一律以第 4 节的前置为前提。

**只读（低风险，最值得先做）**

- 会话：列出会话、看当前会话的轮次与 cwd（`session-cwd.json`）。
- 任务：列出任务、查某条任务的进度与产物。
- 观测：daemon 状态、`daemon.log` 尾部、`mcpCount` / `firstFrameMs` 等指标。
- 本机其它账号的只读状态（单机单人前提下）。
- 回答「我昨天让你干了什么」这类跨会话回忆——聊天记录本身就是归档，读的是会话与任务。

**可写（需要前置与权限设计）**

- 配置：模型 / 权限 / MCP / 工作区，并区分「Agent 真实配置」与「微信独享 overlay」。
- 会话：新建 / 恢复 / 改名 / 删除。
- 任务：停止、续跑、改 cwd。
- 自身扩展：让 Agent 给自己加一个 MCP、补一条技能或记忆。

**通道 / 生态**

- 作为独立 bin 发布，让外部 MCP 客户端直接管理 WeMind。
- 与任务系统结合做定时或事件驱动的自动化。

---

## 4. 若要做，必须先有的前置

1. **内部配置服务**：校验、备份、mtime/size/hash 并发校验、原子写、idle reload 收敛到一处，CLI 与 MCP 共用。
2. **工具契约与最小权限**：读写分离；写操作要能明确「改真实配置」还是「改微信独享 overlay」；沿用控制桥「只有名字与纯数据」的边界。
3. **注入方式**：只在 `managed`（WeMind 托管 MCP）可用，还是 `direct` 也可用；要与三种 `mcpDelivery` 投递方式对齐。
4. **回环检查**：该 server 不得成为 `wechat` MCP 的通道；它与 `wemind-mcp` 是两个不同的 server，命名与检测规则都要区分开。
5. **确认机制**：写操作是否需要二次确认、是否需要审计日志，以及写在哪里。

---

## 5. 明确不做 / 容易误解的点

- 不替代 `wemind` CLI：CLI 仍是本机首选入口，MCP 只是「模型能自己用」的补充。
- 不做「宿主侧工具注册」——ACP 没这个能力，别按这个方向设计。
- 不是「让 WeMind 替用户修 Agent」的通道；Agent 侧自身的问题仍由用户处理。
