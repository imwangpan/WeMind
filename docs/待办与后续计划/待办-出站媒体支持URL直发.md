# 待办：出站媒体支持 URL 直发（图片之外）

> 状态：**待做，排到下一个迭代**。本文只记录结论与做法，不动代码。
>
> 最后核对：2026-11-18 ｜ 相关实现：[远程任务（Worker）：接收、发送非文本消息设计与实现](../设计文档/远程任务（Worker）接收、发送非文本消息设计与实现.md) §19

## 1. 现状

worker（以及 brain）想在回复里发媒体，靠的是一段纯文本约定：

| 类型 | 写法                           | 现在接受什么                       |
| ---- | ------------------------------ | ---------------------------------- |
| 图片 | `![](路径)`                    | 本地绝对路径 **或** `http(s)` 链接 |
| 文件 | `[文件](路径)`、`[附件](路径)` | **只接受本地路径**                 |
| 视频 | `[视频](路径)`                 | **只接受本地路径**                 |

链接出现在文件/视频这一侧时，会被当成普通正文留在消息里（不发送、也不报错）。

## 2. 为什么要改

- 不一致：同样是「外发一个媒体」，图片能直连链接，文件/视频不能，用户无法预期。
- 实际场景：agent 搜到一份公开 PDF、或者某个仓库里的 mp4，本来可以直接发；现在只能让它先 `curl` 落地到工作区再发——多一步，而且失败面更大。
- 技术前提已成立：微信侧上传收的是**字节**（`sendFile({ data, fileName, kind })` → `uploadMediaBytes()`），并不要求「本地文件」。所以这不是能力上限，是解析层的保守选择。

## 3. 当初为什么保守（背景，别丢）

`[文件](https://…)` 与普通 markdown 链接同形，判错就把「用户只想让你自己看的链接」变成了「替他发给对方一个文件」，且不可逆。

不过范围比想象的窄：解析只认**标签恰好是 `附件`/`文件`/`视频`** 的写法（`packages/wechat-daemon/src/daemon/messaging/attachments.ts` 的两条正则），`[参考文档](https://…)` 这类普通链接根本不会触发。

## 4. 方案

1. `extractAttachments()` 遇到 `http(s)` 时不再「保留在正文」，而是产出一个 `remote` 附件项（`{ kind, src, url }`）。
2. 新增下载入口，与图片共用同一套闸：
   - 逐跳 `assertPublicUrl()`（拒绝内网/本机地址），最多 3 次重定向；
   - 超时与大小上限：文件沿用 25MB（`WECHAT_OUTBOUND_FILE_MAX_MB`），视频先按同一上限；
   - 落临时文件（`mode: 0o600`），发送后删除。
3. 失败归因新增 `download`：「这个链接没能下载下来」+ 原链接，写进正文末尾（与现有 `read`/`send`/`budget`/`sensitive` 并列）。
4. 开关：`WECHAT_OUTBOUND_URL_MEDIA=0` 关闭（默认开启）。关闭时行为回到今天的样子（链接留在正文）。

不做的事：

- 不给 `[参考文档](…)` 这类普通标签加支持——只在三个明确标签上生效。
- 不做「正文里的裸链接自动识别」——那是另一件事，歧义更大。
- 不放开 `file://host/…`（UNC）与 NTFS 数据流后缀。

## 5. 风险

| 风险      | 说明                                              | 缓解                                                                          |
| --------- | ------------------------------------------------- | ----------------------------------------------------------------------------- |
| 误判      | agent 写 `[文件](https://…)` 本意是「你自己点开」 | 只在三个标签上生效；失败会在正文里说明，用户能立刻发现                        |
| SSRF      | 链接指向内网                                      | 复用 `assertPublicUrl()`（本机代理把公网解析成 `198.18.x` 的问题另说，见 §6） |
| 体积/耗时 | 大文件下载拖慢回合                                | 25MB 上限 + 超时；下载在发送前同步完成，超时按失败处理                        |
| 带宽浪费  | 下载了但发送失败                                  | 发送失败同样进失败说明，不重试                                                |

## 6. 与 fake-IP 的关系

本机（以及任何挂了「fake-IP 模式」代理的环境）会把公网域名解析成 `198.18.0.0/15`，`assertPublicUrl()` 会判为内网并拒绝。图片通道已经踩到（`拒绝访问本机/内网地址: img1.kuwo.cn（198.18.0.85）`）。做本待办时要一并决定：是否对 `198.18.0.0/15` 网段放行（可配置），否则在代理环境里这条通道等于不可用。

## 7. 验收

真机（沿用 [真机实测：worker 接收 / 发送非文本消息](../审查与质量记录/实测-worker媒体-2026-11-18.md) 的方法）：

1. `[文件](https://…/demo.pdf)` → 收到一个文件；
2. `[视频](https://…/real.mp4)` → 收到一个视频；
3. `[文件](https://192.168.1.1/a.pdf)` → 被拦，正文里出现「没能下载下来」；
4. `[文件](https://…/huge.zip)` 超过 25MB → 被拦，说明是「超过大小上限」；
5. 普通 `[参考文档](https://…)` → **原样留在正文**，不触发下载；
6. `WECHAT_OUTBOUND_URL_MEDIA=0` 时上述 1、2 回到「留在正文」。

单测：一组合法链接、内网链接、非白名单扩展名、超限、重定向超 3 次、`WECHAT_OUTBOUND_URL_MEDIA=0`。
