# 本地双入口：命令派发 + 命令式看/敲（方案 C 迭代）

> 状态：**已实现 ✅**（2026-06-18 首版：task 派发 + cwd 透传 / task-status / task-reply 注入续跑 / task-stop 清理；**2026-10-28 扩展**：多任务/进程池 + 控制桥，见 §13）。
> 关联：[方案C-MVP-远程human-in-the-loop.md](方案C-MVP-远程human-in-the-loop.md)、[方案C-受控ACP工作机设计.md](方案C-受控ACP工作机设计.md)、[repowiki/07-远程任务-Worker.md](repowiki/07-远程任务-Worker.md)。
> 一句话：给 worker 任务加一个**本地终端入口**，与现有微信入口并列——**同一个任务，电脑前用终端管、离开后用微信管**。

---

## 1. 背景与目标

现状（方案 C MVP）：worker 任务只能从**微信单入口**管（派发 `任务：`、回复、`结束任务` 全在微信）。本迭代新增**本地终端入口**：

- **本地派发**：在终端开任务——长描述/多行随便打，且能**指定工作目录 cwd**（微信入口做不到）。
- **命令式看/敲**：在终端查任务状态、回复决策、结束任务。

**微信入口完全保留**；两个入口操作的是**同一套** `task-manager`（1.2.0 起是任务表，见 §13；首版是单任务 `activeTask`）。

**非目标**：实时流式交互视图（设计评估里的「路线 B」，价值与 worker「为远程设计」的定位错位，暂缓）。看是状态快照、敲是命令，**不是**对话式 REPL。

---

## 2. 核心机制：文件桥

CLI（`wemind`）与 daemon 是两个独立进程，worker 跑在 daemon 内。用**轻量文件桥**通信，不引入 socket/端口：

```
本地终端 (wemind)                         daemon 进程
  task "..."        ──写命令文件──►  task-inbox/ ──定时扫描──► dispatchTask/injectTask/stopTask
  task-status       ◄──读状态文件──  task-state.json ◄──关键节点更新── task-manager
```

- **命令方向**：CLI 写「命令文件」→ daemon 定时扫描读取 → 调 `task-manager` → 删文件。
- **状态方向**：daemon 写 `task-state.json` → CLI 读并显示。
- 单向命令 + 单向状态，简单、无依赖、复用现有 `task-manager`。

---

## 3. 文件桥协议

### 3.1 命令收件箱

目录：`~/.wemind/<key>/task-inbox/`，每个命令一个文件 `<时间戳>-<随机>.json`：

```jsonc
{ "kind": "dispatch", "text": "抓取并核实文章X，结果写进笔记", "cwd": "D:\\Product\\xxx", "agent": "opencode", "ts": 1718000000000 }
{ "kind": "reply",    "text": "选方案 B", "ts": 1718000050000 }
{ "kind": "stop",     "ts": 1718000090000, "taskId": 2 }
```

- daemon 扫到按 `kind` 分发：`dispatch`→`dispatchTask(owner, text, cwd, agent?)`、`reply`→`injectTask(owner, text, taskId?)`、`stop`→`stopTask(owner, taskId?)`。处理后**删除该文件**。
- **原子写**：CLI 先写临时文件再 `rename` 进 `task-inbox/`，避免 daemon 读到半截。
- **并发/顺序**：文件名带时间戳 + 随机，daemon 按 `ts` 升序处理。
- **启动清理**：daemon 启动时**清空** `task-inbox/`，作废重启前的残留命令（防重放）。

### 3.2 状态文件

`~/.wemind/<key>/task-state.json`（daemon 写、CLI 读，原子写）：

```jsonc
{
  "active": true,
  "status": "waiting",          // running | waiting | idle
  "to": "<userId>",
  "startedAt": 1718000000000,
  "updatedAt": 1718000060000,
  "turns": 2,                    // 已完成轮次
  "lastOutput": "🤖【任务】我发现两种做法…（截断到 ~500 字）",
  "tasks": [ /* 1.2.0：全部任务各一条（编号/agent/状态/轮次/时长/最近输出） */ ]
}
```

- daemon 在任务**关键节点**更新：派发、每轮输出推送、进入 waiting、停止/完成。无任务时 `active:false, status:"idle"`。
- **1.2.0 起**：顶层字段**镜像最近一条任务**（旧版 CLI 读到仍能显示、不会误判成「无任务」），另带 `tasks` 数组供 `task-list` 列全部；**任务表本身**另存 `tasks.json`（可供重启后续跑，见 §13）。

## 4. CLI 命令（`manage.ts`）

| 命令 | 作用 |
|---|---|
| `task "<描述>" [--cwd <dir>] [--agent <预设>] [<key\|label>]` | 派发任务（写 `dispatch` 文件）。**默认 `--cwd` = 终端当前目录** `process.cwd()`；`--agent` 指定用哪个 agent 跑（缺省 = 默认任务大脑）；默认账号 = default |
| `task-list [<key\|label>]` | 列出全部任务（编号 / agent / 状态 / 轮次 / 时长 / 最近输出） |
| `task-reply <编号> "<内容>" [<key\|label>]` | 回复/注入任务（写 `reply` 文件）；`task-reply 继续` 等价微信回「继续」；多任务时必须带编号 |
| `task-stop [<编号\|全部>] [<key\|label>]` | 结束任务（写 `stop` 文件；不给编号 = 唯一那条，多条并存时会回消歧清单） |
| `task-status [<key\|label>]` | 读 `task-state.json`，显示状态 + 轮次 + 最近输出 |
| `brain switch <预设\|auto> [--worker]` | 热切换对话大脑 / 设默认任务大脑（走控制桥，见 §13） |
| `session list\|new\|resume\|rename\|delete`、`session current` | 会话管理（走控制桥） |

- **`task` 默认 cwd 取 `process.cwd()`**——真正「在哪个目录开就在哪跑」，对标本地直接开 kiro 的体验。
- **daemon 存活预检**：`task`/`task-reply`/`task-stop` 写文件前先检查目标账号 daemon 是否在跑（读 `daemon.pid` + `alive()`，复用 manage 已有 helper）；不在则提示「该账号 daemon 未运行，请先 `start`」，避免命令写了没人消费。
- **派发反馈**：`task` 写完后短轮询 `task-state.json`（约 3s）确认 `active` 变 true 再返回「已派发」；超时则提示「已投递，用 `task-status` 查看」。

## 5. daemon 扫描（独立定时器，不挂在 poller 上）

- poller 是长轮询（`getUpdates` 阻塞 ~25s），**不适合**承载收件箱扫描（会有最长 25s 延迟）。
- `main()` 新增独立 `setInterval`（默认 1s，`WEMIND_TASK_SCAN_MS` 可调）扫 `task-inbox/`：按 `ts` 升序逐个读 → 分发到 `task-manager` → 删文件。
- 该定时器与 poller/worker 并行，互不阻塞（与现有 poller/worker 解耦思路一致）。

---

## 6. cwd 透传（让 worker 在指定目录跑）

- 现状：`worker-acp.ts` 的 `WORKER_CWD` 是模块常量，`ensureProcess` spawn 时用它。
- 改造：
  - `worker-acp.ts` 暴露「下次 spawn 用的 cwd」；`ensureProcess` 用 `pendingCwd ?? WORKER_CWD`；停止时清空 pendingCwd。
  - `task-manager.dispatchTask(to, instruction, cwd?)` 新增可选 `cwd`，派发时设置 cwd 再启动 `runTask`。
- 子进程 cwd 在 **spawn 时固定**，故 cwd 在**派发（首轮）**生效、同任务后续轮次沿用。
- 微信派发不带 cwd → 用默认 `WORKER_CWD`（homedir），**行为完全不变**。
- **1.2.0 修正**：cwd 不再挂在模块级 `pendingCwd` 上——`worker-acp.ts` 已类化为 `class WorkerConn`（每实例自己的 child/cwd/会话），cwd 随**那条任务**的连接走。进程池里同时跑两条不同 cwd 的任务因此互不影响。

---

## 7. 状态落盘（依赖注入，task-manager 不直接碰文件）

- `task-manager.ts` 新增 `setTaskStateSink(fn)`（与 `setTaskPush`/`setTaskTyping` 同款依赖注入）；在 派发 / 每轮 push / 进入 waiting / stop 时调 `fn(state)`。
- daemon 提供 sink 实现：原子写 `task-state.json`（`lastOutput` 截断到 ~500 字）。
- `task-status` 读该文件展示。task-manager 仍不依赖任何文件路径，保持纯逻辑 + 可测。

## 9. 鉴权与安全

- 本地命令默认作用于 **owner（账号本人）** 的任务。能写 `~/.wemind/<key>/task-inbox/` = 本机当前用户 = 机主，**无需额外鉴权**（与微信侧 `allowFrom` 正交，互不影响）。
- worker 仍 `--trust-all-tools`，且本地派发可把 cwd 指向真实项目目录——这等于**机主亲自授权**在该目录全权操作，符合预期（是机主自己在终端开的）。
- 不开任何网络端口，无新增攻击面。

---

## 10. 边界 / 非目标

- 不做实时流式交互视图（路线 B）；「看」是 `task-status` 快照、「敲」是命令。
- ~~沿用**单任务**~~ → **1.2.0 起是多任务**（任务表 + 进程池 + 编号；本地派发不再要求「先结束当前任务」），并发上限 `WEMIND_MAX_WORKERS` 默认 3，超出被拒并提示。详见 §13。
- 不做跨账号批量；命令默认单账号（`key|label` 选择，缺省 default）。

## 12. 风险

- **扫描延迟**：1s 级，派发到 worker 启动有短延迟，可接受（`WEMIND_TASK_SCAN_MS` 可调）。
- **命令文件并发/半截**：CLI 写临时文件 + `rename` 原子入 inbox；daemon 读后即删。
- **daemon 未运行**：CLI 预检 `daemon.pid` + `alive`，不在则提示先 `start`，不静默丢命令。
- **task-state.json 读写**：原子写（临时文件 + rename）。
- **「继续」语义一致**：本地 `task-reply 继续` 与微信回「继续」都走 `injectTask`，行为统一。
- **多账号**：命令带 `key|label`，各账号各自的 task-inbox/task-state，互不串。

## 13. 后续迭代（1.2.0，2026-10-28）：多任务 + 进程池 + 控制桥

首版的「命令收件箱」是**单向**的（CLI 派活，结果从微信回），而且任务侧是**单任务单例**。1.2.0 补了两件事：

### 13.1 任务侧：单任务 → 任务表 + 进程池

- `task-manager.ts` 重写为 `Map<编号, Task>`：编号**按用户单调递增、不复用**（避免「任务 2」在对话里指代漂移），**跨重启不归零**（表在 `tasks.json` 里）。
- `worker-acp.ts` 从模块单例改为 `class WorkerConn`（每实例一条连接），`worker-pool.ts` 管复用/回收/上限：**同 agent 空闲命中 → 回收最旧空闲腾位 → spawn**；并发上限 `WEMIND_MAX_WORKERS`(3)、空闲上限 `WEMIND_IDLE_MAX`(2)、空闲回收 `WEMIND_WORKER_REAP_MS`(5min)。结束「等你回复」的任务时进程**回池**（不再杀）；结束「正在跑」的那条仍只能力杀（ACP 回合没法优雅取消）。
- 派发时可指定 agent（`--agent <预设>` / 微信 `任务 <预设>：正文`），缺省用**默认任务大脑**（`切换任务大脑` 可改进程内粘性值，不落盘）。
- 重启后未完成的任务标「已中断」，回「继续」/`#n` 才按 agent 能力 `session/load|resume` 续跑（**不自动**拉起）。

### 13.2 桥侧：新增双向「控制桥」

切换大脑、开新会话、恢复会话都必须发生在 **daemon 进程里**（进程内的 ACP 连接、会话指针、任务表都是它的活状态）；而且 CLI 需要**当场知道成没成**（要打印结果、要给退出码）。于是新增双向桥 `control-bridge.ts`：

```
wemind session new 周报
  └─ 写 control-inbox/<ts>-<id>.json ─► daemon scanControlInbox（先 unlink 再执行）
                                          └─ handleControlRequest ─► 与微信指令**同一段实现**
                                          └─ 写 control-out/<id>.json { ok, text }
  └─ 短轮询 control-out/<id>.json（默认 30s 超时；brain.switch 自动放大）→ 打印 + 退出码
```

- **幂等与防重放**：daemon 启动时清空两个桥目录；处理时先删请求文件再执行；`controlBusy` 一次只处理一条。
- **`.bridge` 凭据**：daemon 把**自己的 pid** 写进 `control-out/.bridge`。CLI 拿它与 `daemon.pid` 比对，对不上 → daemon 在跑**旧版本**（不认识桥）：**必须由 daemon 执行**的命令（`session new|resume`、`brain switch|worker|handoff`）**发出前**拒绝并给出「`wemind stop <key> && wemind start <key>`」；**文件类**命令照常——`session rename|delete` 直接改登记表、`session list` 直接读登记表（附一行「按下次会用的那个大脑列」的说明）、`task-list`/`task-status` 读 `tasks.json`（从不过桥，只在 daemon 没跑时注明「上次快照」）。这把 30s～165s 的静默等待换成一句能照做的话。
- **安全边界**：请求字段只有 `target`（**预设名**）/`ref`/`name`/`text`/`taskId`/`page`——**没有 `bin`/`args`/`shell` 的位置**。伪造请求最坏只能「选一个已装的 agent 或清掉自己的会话」，不能让 daemon 执行任意程序。`parseControlRequest` 是唯一入口校验。
- **`brain set` 的热应用边界**：`wemind brain set <预设>`（只给预设名、不带 `--restart`）在 daemon 在跑**且认桥**时走桥热应用（等价 `brain switch`：先预热、**成功才落盘**，失败回滚并回执写明「brain.json 没有被改写」，要强制落盘用 `--restart`）；带 `--bin`/`--args`/`--shell` 时**不走桥**，仍是「只写盘 + 需重启生效」——刻意如此。

### 13.3 新命令面

| 命令 | 作用 |
|---|---|
| `brain switch <预设\|auto> [--worker]` | 热切换对话大脑（`--worker` = 设默认任务大脑，粘性不落盘） |
| `brain handoff` | 生成交接摘要（切到别的大脑后第一条消息注入一次） |
| `session current` / `list` / `new` / `resume` / `rename` / `delete` | 会话管理；`list`/`rename`/`delete` 在 daemon 不在时降级为直接读文件 |

### 13.4 落地步骤与验证（1.2.0）

单测：`worker-pool`（策略纯函数）`pool-spawn`（真起进程验复用/回收）`task-store`（落盘/降级/编号连续）`task-manager`（编号/消歧/上限/停止）`control-bridge`（形状/校验/**bin-args-shell 进不来**）`pid-record`（三种 pid 文件形态）；端到端用「真 daemon + 假 ACP agent + 独立临时账号」验过全链路（14 条命令往返、`.bridge` 守卫、旧版本降级）。
