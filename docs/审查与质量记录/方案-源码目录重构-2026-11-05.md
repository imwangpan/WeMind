# `packages/wechat-daemon/src/` 目录重构方案（2026-11-05）

> **状态：设计方案，未实施。** 本方案在文档审计分支（`docs/full-audit-2026-11-05`）上产出，实施排在文档审计合并之后，**单独开分支**做。
>
> **最后核对**：2026-11-05（针对当时的 `src/` 快照：117 个文件 = 57 源 + 60 测试）

## 1. 问题

`packages/wechat-daemon/src/` 目前 **117 个文件全部平铺在同一层**：57 个源文件 + 60 个 `*.test.ts`。带来三个具体问题：

1. **没有子系统边界**。`index.ts`（1103 行，入口编排）、`brain-agents.ts`（961 行，预设表）、`version.ts`（25 行）、`atomic-json.ts`（25 行）在同一个列表里；新增一个模块要自己判断「该不该和它们放一起」，没有答案。
2. **源码与测试混合，看不出归属**。60 个测试里有 **11 个没有同名源码**（`acp-switch`、`brain-record`、`pool-spawn`、`sandbox-{claude,cline,dsh,gemini,kiro,opencode,pi,qoder}`），平铺时只能靠读 import 才知道它测的是谁；反过来 **8 个源码没有同名测试**（`acp-brain`、`brain-switch`、`cli-brain`、`cli-task`、`cli`、`mcp-sandbox`、`worker-acp`、`worker-sandbox`），看起来像「没测试」。
3. **浏览成本**。按字母排序后 `acp-*`、`brain-*`、`cli-*`、`task-*` 各自成块，但跨块的调用关系（谁依赖谁）完全看不出来。

## 2. 业界做法与选择

| 做法 | 代表 | 优点 | 代价 |
| --- | --- | --- | --- |
| **A. 同目录 co-location**（`x.ts` 与 `x.test.ts` 相邻） | Vitest / Rust / Go 社区主流 | 改一个模块只在一个目录里看；测试与被测代码永远同路径；无需改 `vitest.config.ts` 的 `include` | 目录内仍是「源码 + 测试」混合 |
| **B. 每个特性目录下 `__tests__/`** | Jest 传统 | 目录里只剩源码 | 测试 import 全变 `../x.js`；多一层空壳目录；TS 生态里 `__tests__` 已是弱约定 |
| **C. 包根 `test/` 镜像树** | 部分 Node 项目 | 源码树完全纯净 | 60 个文件移出 `src`，`tsconfig.include` 要加目录；「哪个测试覆盖这个文件」只能按路径猜；跨模块的 `sandbox-*` 系列更难定位 |

**选 A。** 决定性理由：本项目测试**重度依赖「先设环境变量、再动态 import」**（`acp-switch.test.ts`、`agent-slot.test.ts`、`sandbox-qoder.test.ts` 都在文件头 `mkdtemp` + 设 `WECHAT_DATA_DIR` 后 `await import(...)`）。B/C 会把这些 `await import("../agents/brain-agents.js")` 推得更远，路径漂移风险上升，而 A 保持「同一目录里 `./x.js`」的最短路径。

同时说明一个判断：**真正让目录「乱」的不是源码与测试混合，而是没有特性边界**。分成 8 个目录后每目录 5–24 个文件，混合已不影响阅读；因此本方案不引入 `__tests__` 或独立 `test/`，只做分层 + 就近放置。

## 3. 目标树

```
packages/wechat-daemon/src/
  cli.ts                      # bin 入口（tsdown entry，位置不变）
  index.ts                    # runDaemon() 入口（位置不变）
  daemon/                     # 微信侧本体：路由 / 指令分派 / 进度 / 外发 / 收件箱 / 媒体
  acp/                        # ACP 协议层 + 大脑进程与切脑
  agents/                     # 预设表 / 配置 / 状态 / 沙箱 / MCP 视图
  tasks/                      # 多任务、worker 池、任务收件箱
  sessions/                   # 会话登记表、当前会话表、会话指令、交接
  cli/                        # CLI 子命令 + 三套常驻外壳
  ipc/                        # 控制桥 + 命令表（两个入口共用的契约）
  shared/                     # 无业务依赖的基础件
```

### 3.2 依赖方向（单向，无环）

```
shared ← agents ← acp ← daemon ← 根入口（cli.ts / index.ts）
                    ↖ tasks
sessions、ipc 被上游依赖，自身只依赖 shared
cli/ 只向下依赖（agents / acp / sessions / tasks / ipc / shared）
```

**两处必须一起处理的边**：

- `acp-brain.ts → handoff.ts`（acp 依赖 daemon 的 handoff）→ 把 `handoff.ts` 放进 `sessions/`，边变成 `acp → sessions`，与既有的 `acp-brain → session-map / session-registry` 同向，不构成环。
- `pid-record.ts → brain-agents.ts` 是 **`import type`**，编译期擦除，不产生运行时环；保留即可，但要在 `shared/README` 或注释里写明「shared 只允许 `import type` 向上引用」。

### 3.3 命名调整（顺手做，低风险）

| 现在 | 改为 | 理由 |
| --- | --- | --- |
| `acp-switch.test.ts` | `acp/brain-switch.test.ts` | 它测的就是 `brain-switch.ts`；当前名让 `brain-switch.ts` 看起来「没测试」 |
| `brain-record.test.ts` | `cli/brain-record.test.ts` | 测 `manage.ts` 的 `brainRecord` 导出 |
| `pool-spawn.test.ts` | `tasks/pool-spawn.test.ts` | 测 `worker-pool` 的 spawn/复用路径 |
| `sandbox-*.test.ts` | 保持名，进 `agents/` | 文件名已按 agent 区分，无需改 |

### 步骤 2：改写 import（约 119 行）

规则：**同组 import 仍是 `./x.js`；跨组改成 `../<组名>/x.js`**。

统计口径（按 §3.1 分组算）：同组 116 行不变，跨组 119 行需要改；受影响文件 88 个（每个含相对 import 的文件都要过一遍，因为即使 import 目标同组、文件本身换目录也要检查相对路径）。

做法：写一次性 codemod 脚本（`scripts/codemod-src-layout.mjs`，用完即删或留在 `scripts/` 备查），输入「文件 → 新路径」映射 + 解析旧目标的新位置，逐文件改写 `from "./x.js"` / `await import("./x.js")` / `typeof import("./x.js")` 三种形态。**注意测试文件里的动态 `await import(...)` 与 `vi.mock(...)` 字符串参数**——这些也是路径，正则要覆盖。

### 4.5 文档同步流程（重构期间）

**原则：移动一批文件，就同步这一批涉及的文档，不攒到最后一次性补。** 一次性补最容易漏，而且漏了没有任何东西会变红。

#### ① 重构开始前（一次性准备）

1. 确认 `scripts/doc-impact.mjs` 与规则表已落地，且 `restructure` 规则存在（定义见 [`文档守卫设计.md`](../设计文档/文档守卫设计.md) §3.3 / §3.4）。
2. 记录基线：`npm run verify` 全绿。
3. 跑一次 `npm run doc-impact`，确认重构尚未开始时无规则触发（避免把无关改动算进来）。

#### ② 每完成一个目录的移动（重构进行中）

1. **改代码的同时改文档**：以「一个目标目录」为一批（如 `git mv` 完 `acp/` 的 6 个文件后立刻处理），同步更新引用这些路径的文档。

2. **要改的文档从三个来源找，缺一不可**：
   - `npm run doc-impact`：`restructure` 触发后打印「目录结构文档」清单；
   - 本方案 §4 步骤 4 的清单（14 个文件、87 处引用）；
   - `git grep "src/<旧文件名>"`：按旧路径全库搜一遍，grep 结果就是这一批要改的准确位置。三篇只写文件名、不带 `src/` 前缀的文档（repowiki/01、06、07、09、10、11 等）不需要改。

3. **历史文档按约定处理**：
   - `docs/审查与质量记录/审查-2026-11-02.md`、`CHANGELOG.md`、`docs/设计文档/*`：**只加一行**「当时路径，现为 `src/<新路径>`」，不改正文；
   - 本方案（`方案-源码目录重构-2026-11-05.md`）自身属于设计稿，实施完成后在文首标注「已实施」，正文路径保持当时的快照。

#### ③ 每个提交前（必跑）

```bash
npm run doc-impact:check        # restructure 规则：目录结构文档至少改了一个
pwsh -NoProfile -File scripts/check-docs.ps1   # 相对链接没有断
```

`doc-impact` 不做全量强制：`restructure` 只要求 `AGENTS.md`、`docs/ai/README.md`、`docs/repowiki/02-系统架构.md` 至少改一个，其余路径引用靠本方案清单与 grep 逐项核对。**这一条是刻意设计**——历史快照文档不允许改正文，如果强制 14 个文件全改，检查会永远变红，机制随即失效。

#### ④ 重构完成时（验收）

1. `git grep "src/<旧文件名>"` 零命中（历史快照除外，且快照里已加「当时路径」说明）；
2. `npm run doc-impact:check` 通过；
3. `npm run verify` 全绿（含断链检查）；
4. PR 描述里列出「本次同步的文档」清单，与本方案 §4 步骤 4 的 14 个文件逐一对应。

#### ⑤ 提交划分建议

目录重构与文档同步放在**同一个 PR**，但可以分成三个提交，便于 review 和回滚：

| 提交 | 内容 |
|---|---|
| 1 | `git mv` 纯移动 + 改名（不改内容） |
| 2 | import / 非代码引用改写（codemod） |
| 3 | 文档路径同步（§4 步骤 4 的 14 个文件） |

三个提交都必须在该 PR 内；不允许「先合代码、文档下个 PR 补」——这正是 `doc-impact` 要防的情况。

## 5. 风险与回滚

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 漏改一处 import → 构建失败 | 119 行跨组改动，人工易漏 | 用 codemod 脚本 + `npm run typecheck` 兜底（TS 会精确报「找不到模块」） |
| 测试里的动态 import / `vi.mock` 字符串漏改 | 这些不经过类型检查，只在运行时炸 | codemod 正则显式覆盖 `await import("...")`、`typeof import("...")`、`vi.mock("...")`；跑全量 `npm test` |
| `version.ts` 上移一层后读不到版本 | `readOwnVersion` 是循环向上找 `package.json` | 移一层**不影响**（仍会找到 `packages/wechat-daemon/package.json`）；用 `wemind version` 验证 |
| `import.meta.url` 相关的其它路径假设 | 已核对：只有 `version.ts`、`manage.ts`（用 `process.argv[1]`，与目录无关）、`image-reply.ts`（处理 `file://` 输入，与自身位置无关） | 无需改动 |
| `.worktrees/` 里的旧副本干扰测试 | vitest 已排除 `**/.agents/**`，但 `.worktrees/` 未排除 | 若在 worktree 里做，确认 `vitest.config.ts` 的 exclude 是否需加 `**/.worktrees/**`（**待实测**） |

**回滚**：单提交，`git revert <sha>` 即恢复；因为是纯 rename + 路径改写，revert 不会碰到任何逻辑改动。

## 6. 不做的事（明确排除）

- **不拆文件**。`index.ts`（1103 行）、`brain-agents.ts`（961 行）的行数问题属于「职责拆分」，与「目录分层」是两件事；本方案只移动，不改内容。拆 `brain-agents.ts`（预设表可以按 agent 拆成数据文件）留作后续独立任务。
- **不引入 `__tests__/` 或独立 `test/`**（理由见 §2）。
- **不改包边界**。仍是单包 `@wemind/cli`，tsdown 仍打单文件 `dist/cli.js`。
- **不动 `wechat-ilink-core` / `wechat-mcp`**。它们的 `src/` 已经有子目录（`api/`、`store/`、`cdn/`、`tools/`），规模也小（core 约 20 个源文件），无需同批处理。
