> 从 [`AGENTS.md`](../../AGENTS.md) §6 拆出（2026-11-09）。按关键词检索，不需要通读；每条标注各自的核对日期。正文提到的 `docs/…`、`packages/…` 路径均相对仓库根，链接按本文位置解析。

> **2026-11-12 起的路径口径**：默认 `homeMode=real`，Agent 配置根是 `<账号>/agent-view/<role>/<agent>/`（未覆盖项链接真实 home），默认工作区是 `<账号>/workspace/{brain,worker}`，入站媒体在 `<账号>/media/inbound`。本文中 2026-11-12 之前写的「沙箱 / `BRAIN_HOME` / `brain-home`」是 `sandbox` 模式的实测记录；`real`/`mirror` 下这些结论仍适用于协议能力，但路径换成配置视图。需要复现旧路径时显式设 `homeMode=sandbox`。

- **配置视图的 override 路径必须按平台归一化，否则会写穿到真实配置（2026-11-12 修）**：预设里的路径常写成 `settings/mcp.json`（正斜杠），而 `path.join()` 在 Windows 产出 `settings\mcp.json`。如果 `overrideRelPaths()` 不做 `path.normalize()`，`hasOverriddenChild("settings", …)` 会漏判，整个 `settings/` 被建成 junction；随后 `ensureKiroV3Permissions()` / MCP 生成器写 `settings/mcp.json` 就会穿透到真实 `~/.kiro/settings/mcp.json`。修复包含两件事：① 比较前统一 `path.normalize()`；② 构建时若发现 override 路径上残留旧 junction/符号链接，先断开再建真实目录，父目录含被覆盖子项时也要先拆父链接。回归用例在 `config.test.ts` 的「override 路径归一化」与「上次构建留下的父目录 junction…」。新增 Agent 的 `mcpConfigFile` / `settingsBase` / `extraConfigFiles` 时，必须确认它们在视图里是真实文件而不是父目录链接。

- **两个输出出口，别再直接写 console（2026-11-11 收敛）**：之前 5 份自造 `log`/`dlog` 各拼各的 `[wemind/...]` 前缀，另有 17 处裸 `console.error`、77 处裸 `console.log`，非常混乱。现在运行日志统一走 core `logging.ts` 的 `createLogger(scope)`，输出 `[wemind/<scope>][INFO|WARN|ERROR|DEBUG] …` 全部 stderr；CLI 用户输出走 stdout 的 `print()`（纯文本、无前缀、无级别——CI 冒烟断言 `wemind version` 原文、readline 用 `process.stdout` 配对，改了就坏）。级别写进文本而非分流，是因为 watchdog 合并 stdout/stderr 后通道信息会丢。**DEBUG 是预留级别**：现在没有调用点，帧级关键线索（`spawn`/`initialized`/`session/new`/`prompt ok`）都归 INFO，因为排障必须可见；将来要打逐帧原始 payload 时用 `logger.debug` + `WEMIND_LOG_LEVEL=debug`。`wemind log --errors` 认新标记，旧日志按关键词兼容（轮转掉后可删兼容清单）。
- **`daemon.log` 是全量运行日志，不是错误日志（2026-11-11 核对）**：运行日志统一由 `core/logging.ts` 的 `createLogger(scope)` 写到 stderr（daemon 本体、ACP、worker、task、watchdog，以及 `run-daemon.ps1 -Mode shell` 的包装行都带 `[LEVEL]`），watchdog 把子进程 stdout/stderr 合并进 `~/.wemind/<账号>/daemon.log`；**有级别标记、没有单独的错误文件**。用 `wemind log [key|label]` 看尾部（默认 50 行，保留上下文），`--errors` 按 `[ERROR]/[WARN]` **精确筛选**（升级前写入、没有级别标记的旧日志才回退到关键词清单：含 `退避`/`限流`/`过期`/`挂起` 等），**每条命中还带前后各 2 行上下文**保留因果；`--file 1` 看轮转出去的旧日志（默认 10MB × 3 份，报错常常已经滚走了）；**别假设文件里只有错误**，也别只看当前 `daemon.log` 就断言「没日志」。2026-11-11 起 `getUpdates error` 这类重复网络失败由 `shared/io/repeat-log.ts` 节流（第 1 次 + 每 60 次带「连续 N 次」+ 恢复时一条 INFO），不再刷满 10MB 把线索顶走；启动行带 `up. v<版本>`，贴日志时能看出跑的是哪版。命令是一次性快照，不带 `--follow`（轮转靠改名，跟随句柄会指向旧文件）。
- **常驻循环意外退出会变成「僵尸 daemon」（2026-11-11 修）**：`void pollerLoop(...)` / `void fastWorkerLoop(...)` 原先没有 `.catch`，一旦在各自 `try` 之外抛错，进程还活着、pid 文件还在、`wemind list` 显示「运行中」，却再也不收消息，日志只剩一行 `unhandledRejection`。现在 `fatalLoop()` 打印映射后的 `.ts` 行号并 `process.exit(1)`，由 watchdog 5s 重拉（`WEMIND_MAX_RESTARTS` 防崩溃风暴）；`controlInbox.scan` 的定时调用也补了 `.catch`。
- **Windows 进程身份查询是三态，不是布尔（2026-11-12 加固）**：`proc-identity.ts` 的 `commandLines()` 返回 `{lines, error}`，`identifyProcess()` 返回 `ours/other/unknown`。查询失败（PS 缺失 / CLM / 权限）时 pid 仍活着但查不到命令行 → `unknown`：`start` 与 watchdog 单实例守卫 fail-closed（拒绝启动，防双开抢 token），`stop` 不杀且保留 pid 文件，`wemind list` 显示「无法确认」。**不要把 `unknown` 并进 `other`**——那等于「查询失败就放行」。PowerShell 解析走 `shared/process/powershell.ts`：优先系统自带 5.1（固定路径），缺失回退 `pwsh`；Windows 输出用 `WEMIND|pid|base64(UTF-8)`，避免中文 Windows 的 CP936 把命令行解码成乱码。

- **provider 报错的任务转「已中断」（2026-10-29；2026-11-02 路由改版后仍保留）**：`task-manager.ts` 的 `providerIssue()` 认出模型/账号侧错误（额度/余额、密钥鉴权、计费、模型不存在）→ 该任务**直接转「已中断」**（状态如实反映这轮没跑完，也别停在「等你回复」误导用户）→ 账号修好后回 `#n 继续` 续跑（可续跑任务唯一时裸「继续」直接续跑，多条时回编号清单）。判据是关键字表（错误措辞来自各 agent 的 provider、不统一），**限流优先不归类**（先查 429/rate limit/overloaded 再查账号关键字：Google 的按分钟 429 原文就写着「Quota exceeded … requests per minute」，顺序反了会把限流误判成额度问题）；**认不出的一律按老规矩停在「等你回复」**——宁可多误判一次，也不把偶发失败误判成账号问题。改这里的判据别顺手放宽。
- **`daemon.log` 会轮转（2026-11-02）**：内置 watchdog 把子进程 stdout/stderr 接成管道，由 `log-rotate.ts` 的 `RotatingLog` 逐块追加并在运行中轮转（`WEMIND_LOG_MAX_MB` 默认 10、`WEMIND_LOG_KEEP` 默认 3；`daemon.log.1` 最新，`0` = 不留历史）。`scripts/run-daemon.ps1 -Mode shell` 在每次重拉前轮转（默认 cli 薄壳走 builtin，由内置轮转负责）；pm2 runner 交给 `pm2-logrotate`（repowiki 10）。轮转只能用「每次打开→写→关闭」，Windows 上不能改名仍被写入进程持有的文件——改 watchdog 时别换回继承 fd。
- **长大脑回合不再阻塞任务/控制指令（2026-11-02）**：消息入队时按 `isFastLane()` 分两条队列——控制指令与任务指令（含确实有可续跑任务的「继续」短句）进 `fastQueue`，由 `fastWorkerLoop` 与大脑回合并发处理；其余进 `msgQueue` 串行喂大脑。切脑/会话/交接仍要操作同一个 ACP 连接，会在 ACP 门口等当前回合结束（语义要求）；快车道命令之间串行保序，发送共用 `replyChain` 与连发额度。改路由时两条队列都要看，别只改 `workerLoop`。
- **无编号消息默认归大脑（2026-11-02 改）**：此前是「只要有一条 waiting 任务，任何无前缀消息都喂给它」——真机两次被陈旧任务吞掉（#26、#28：任务早已出完结果，用户想找大脑聊天，消息却进了任务）。现在 `task-manager.shouldResumeTask()` 只放行「继续 / 接着跑 / continue」这类短句，且必须存在可续跑任务（有 waiting；或没有活跃任务时存在 interrupted——多条时任务侧回编号清单，不替你选）；其余一律走大脑。任务追问一律显式寻址：`#<编号> 正文`（全角 `＃`、全角冒号 `：` 均可；半角冒号留给时间 `#1:30`）、`> 正文`（明确发给任务的短前缀；没有任务时会新开一条）、`任务 …`。每条任务结果/中断推送末尾都会带一行 `↩ 回这条任务用「#28 正文」；不带前缀的消息会交给大脑。`——改路由时这行必须跟着改，用户就是靠它学写法的。**真机验证（2026-11-02）**：waiting 任务 #29 在表里时，无前缀「只回复数字 7」走大脑（回复 7），`#29 只回复数字 8` 才进任务。
- **大脑侧的 provider 报错也只试一次（2026-10-29）**：agent 会把 provider 的一切回合失败都包成 `-32603 … turn failed: …`，所以余额不足这类**永久**错误按协议错误码看就是「后端瞬时错误」——老口径重试 3 次（每次都要冷启动一个 agent 进程），最后丢给用户一句「稍后把消息再发一次」。现在 `daemon-routing.ts` 的 `brainFailurePlan()` 先过与任务侧**同一张** `providerIssue()` 关键字表：认出额度/余额、密钥鉴权、计费、模型不存在 → **只试 1 次**，并直接把原因回复给用户（「（这次没答上来：额度/余额不足。这类问题重试不会好——把账号/模型处理好后把消息再发一次就行）」）；「密钥/鉴权」「模型不可用」两类再加一句**要重启一次 daemon** 才会读到新登录态/模型（运行中的 daemon 不重读 brain.json、不重新同步凭据）；**限流优先仍按 backend 重试 3 次**（判据顺序别改）。日志行 `brain error (try 1, provider：额度/余额不足)`。
- **VS Code 集成终端里 `wemind start` 会「假启动」（2026-10-29 修）**：VS Code 的「智能自动附加」给终端里每个 node 注入 `NODE_OPTIONS=--require <…>/ms-vscode.js-debug/bootloader.js` + `VSCODE_INSPECTOR_OPTIONS`（`deferredMode:true`），被注入的进程要**等调试器接上才执行主脚本**；终端里的前台命令会被接上（`stop`/`list` 看着一切正常），但 `start` **脱离出去的后台守护进程不会被接** → 进程活着、一行 JS 不跑：答复说「已启动」，实际 `daemon.log` / `wrapper.pid` 不更新、daemon 没起（`wemind list` 显示未运行，进程表里只有一个没有子进程的 `cli.js _watchdog`）。现在 `watchdog-runner.ts` 的两次脱离式 spawn 都过 `debug-env.ts` 的 `stripVscodeDebugEnv()`：只摘 VS Code 自己那段 `--require`，用户其它 `NODE_OPTIONS` 原样保留。**前台 `wemind daemon` 的 ACP 子进程同样要摘**（`spawn-agent.ts` 的 `spawnEnv()`）：否则 daemon 自己跑得好好的，它 spawn 的 agent（多为 node 脚本）却继承 bootloader、等调试器等到 `initialize` 超时。同一注入也是「本机跑测试偶发超时」的原因——测试用 `NODE_OPTIONS=` 前缀跑。
- **`wemind start` 不再继承 `WECHAT_DATA_DIR`（P0 修复，2026-11-07）**：`WECHAT_DATA_DIR` 是 `account.ts` 里**最高优先级**的目录解析项，本意只给 `wemind daemon` 直跑做一次性覆盖（开发/CI）。用户把它 `setx` 成永久变量后，`wemind start <key>` 会按它寻址而不是 `<根>/<key>`，产生三种静默失败：**静默空转**（目标目录已有 daemon：新 watchdog 看到那里的 `wrapper.pid` 后直接退出，或 daemon 以退出码 75 退出；答复却说已启动）、**起错账号**（`WECHAT_DATA_DIR` 指向 A 的目录，用户以为在起 B）、**停不掉**（pid 写进别处，`wemind stop` 找不到）。现在启动器（`watchdog-runner` / `pm2-runner`，以及 `login --start`、Windows 自启任务走的同一条 `startDaemon`）统一经 `shared/launcher-env.ts` 的 `launcherEnv()`：丢弃 `WECHAT_DATA_DIR`（空串也丢）、保留 `WEMIND_HOME`/密钥、强制覆盖 `WECHAT_ACCOUNT`；变量指向非预期目录时向 **stderr** 打一条迁移指引（此时账号目录尚未解析，不能写 `daemon.log`）。Linux/macOS 的自启单元直接跑 `daemon`，用 `Environment=WECHAT_DATA_DIR=` 空值覆盖用户管理器里的旧值。`wemind daemon` 直跑**不经过**该函数，覆盖语义保持不变。守卫：`launcher-env.test.ts`。
- **开机自启：触发器只跑 `start` / `daemon`，绝不跑 `autostart install`（2026-11-07）**：Windows 计划任务的动作是 `wemind start --all`（只装部分账号时是 `start <key…>`），重拉交给内置 `_watchdog`；Linux systemd / macOS LaunchAgent **本身是 supervisor**，单元必须跑 `wemind daemon` 前台常驻——跑 `wemind start` 会在它退出后判定「服务已退出」并无限重拉（systemd 默认 `KillMode=control-group` 还会连带杀掉 detached 的整条 cgroup）。若触发器写 `autostart install`，每次登录都会再执行一遍安装。其他细节：`New-ScheduledTaskSettingsSet` 不显式给 `-ExecutionTimeLimit ([TimeSpan]::Zero)` 时默认 **PT72H**，三天后任务被杀；计划任务以**当前用户**、`AtLogOn` 注册即可（`/RU SYSTEM` 落 Session 0 且要管理员，拿不到用户环境）；`TaskSettings.Hidden` 不是「隐藏窗口」；受管机器禁止建计划任务时自动降级到 `HKCU\...\Run`（无需管理员，但会出现在「任务管理器 → 启动」）。检测到 PM2 时优先用 PM2（实例名 `wemind-<key>`）；两套并存会抢同一个 bot token，`install` 会要求人工确认后只留一套。安装时记录的可执行文件路径必须用 `stableExecPath()`（`fs.realpathSync` 的容错包装）解析：fnm 的 `fnm_multishells` 是每个 shell 临时创建的联接目录，直接写 `process.execPath` 会在该 shell 退出或重启后失效（Windows 真机已验证真实路径落在 `%APPDATA%\fnm\node-versions\<版本>\installation\node.exe`）；内置 watchdog 与 pm2 runner 启动子进程时也走同一解析。Linux/macOS 的服务单元是按安装时的账号逐个生成的，新增账号要重新运行 `wemind autostart install`。**旧版启动文件夹项（`wemind*.vbs` / `.bat` / `.cmd` / `.lnk`）不会自动清理**：它调用 `wemind start`，而 `startDaemon()` 会先 `stopDaemon` 再起新链，登录时会打断任务刚拉起的 daemon（Windows 真机实际遇到一个 2026-10-16 遗留的 `wemind-daemon.vbs`）；迁移时手动删除，只留 `autostart install` 一套。Linux/macOS 分支**尚未真机验证**（🟡）。
- **权限口径（2026-10-29 统一，平台事实已确认）**：**必须扫码登录该 bot 才能给它发消息**（微信平台限制），所以每个 bot 只有它的**登录者**（扫码登录它的那个微信号）能发。文档一律用「**登录者**」与「**登录者白名单**（`allowFrom`，**默认拒绝**；它是**兜底校验**，正常只含登录者一个 userId，防发送范围变化/别的入口）」，作用范围写成「**整个账号（仅登录者）**」/「**登录者的会话**」/「**登录者的任务**」；**禁用**「账号本人 / 授权用户 / **主号 / 主账号**」——「主号」会被读成「多个微信账号之间有一个有权限的主号」，`label` 只是别名（示例统一用 `工作号`）。**一个微信账号 = 一个真人、一个 daemon**：微信侧换大脑只能由该账号的登录者切**它自己**那个（`OWNER_ONLY_KINDS`），本机 CLI 才能用 `key|label` 指定任意账号（范围/限制/两入口区别见 README「多账号管理」与 `docs/repowiki/06`「多账号下的范围、两个入口」）。
- **重启后旧 `context_token` 期间的外发要挂起（2026-10-29 修）**：`state.contextTokens` 从磁盘恢复，daemon 重启后仍是上次运行留下的 token；该用户发来下一条消息之前，任务结果（`setTaskPush`）与 CLI 指令答复（`sendNotice`）必然 `ret=-2 (prepare failed)`，`reply()` 重试仍是同一个旧 token（修复前**静默丢失**，真机复现：任务跑完只在 `任务列表` 里看得到）。现在这类「必须送达」的外发**只在该用户本进程还没发过消息时**（`freshTokenUsers`）失败才挂进 `pending-push.ts` 的内存队列（每人 20 条、超出丢最旧）；该用户下一条消息一到，poller 等这一批消息的计数重置**全部做完**后补发（每个发件人一次）：按入队顺序、计入连发额度、每轮最多 5 条且不越过本回合留给答复的额度，排在该批消息触发的进度/答案之前；重置计数改按「还没发完的条数」（`inflightSends`）算、不清零——否则排队中的发送会把最终答案挤到限流上。补发失败（任何原因）重新挂起，同一条最多 3 次。本进程收到过该用户消息之后，`-2` 按限流处理、不挂起；回合内的普通回复不挂起。队列不跨重启（任务结果仍在 `tasks.json`）。日志关键词「`send -2（旧 token）→ 挂起`」「`新 token 已到 → 补发挂起消息`」「`补发 N 次仍失败 → 重新挂起`」「`放弃这条挂起的推送`」。
- **消息 ID 是 uint64，不能当 JS number（P0，2026-11-09 修）**：iLink 的 `message_id`（以及部分回包里的 `msg_id`/`svr_id`）会到 `7525…` 量级，超过 `Number.MAX_SAFE_INTEGER`；直接 `JSON.parse` 会把相邻 ID 舍入成同一个数，随后 `>` 比较会**漏消息**。core 的 `parseJsonWithLosslessIds()` 在 `JSON.parse` 前给这些字段加引号（只改 ID 字段，不碰字符串内容；按完整 JSON number token 读取，`1.5`/`7.0e2` 这类非整数原样保留，改写失败时退回原始文本解析，且仅当「原文合法、改写后反而非法」时打一条 warn（说明改写逻辑可能坏了），不让通道停摆），`ServerState.lastMessageId` 改存字符串，去重另存最近 200 条 `seenMessageIds`（旧数字游标首次读取时用 `normalizeMessageId` 迁移）。**改游标/去重时不要写 `Number(id)`、`id > last`**，统一用 `compareMessageIds`/`maxMessageId`/`rememberMessageId`。守卫：`message-id.test.ts`、`client.test.ts`、`account.test.ts`、`messages.test.ts`（MCP）。
- **出站附件只认显式语法，且路径不是「随便读」（2026-11-09）**：brain 必须写 `[附件](file:///绝对路径)` / `[文件](...)` / `[视频](...)`（路径含 `)` 时用 `[附件](<路径>)`；普通形式遇到 `(` 不猜、整段保留为正文）；普通 `[文字](路径)` 或裸路径不会被当成附件（避免把正文里的普通链接误发成文件）。**只允许本机绝对路径**：`file://host/...` 与 UNC `\\server\share` 一律拒绝（`realpath`/`stat` 会触发 SMB 认证，是提示注入可用的外泄/挂起面），软链接/junction 也先看链接目标、再看 `realpath` 结果；Windows 另外拒绝 **NTFS 数据流后缀**（`account.json::$DATA` 会让 `path.basename()` 变成 `account.json::$data`，绕过所有按名规则）。读取前 `realpathSync`，随后拒绝 `account.json`/`state.json`/`brain-*.json`/`session-registry.json`/`worker-sessions.json`/`handoff.json`/`tasks.json`/`task-state.json`/`allow-from.json`/`workers.pid.json`/`.env*`/`*.pem|key|p12|pfx|jks|keystore`/SSH key（`id_rsa|dsa|ed25519|ecdsa`，含 `_sk`）/文件名含 secret(s)/credential(s)/cred(s)/token(s)/password(s) 的文件、`.auth/` 目录，以及各 agent 的登录态（`.credentials.json`/`.credentials.yaml`/`oauth_creds.json`/`google_accounts.json`/`auth.json`/`providers.json`/`models*.json`）；`settings.json`/`models*.json` 在数据目录（brain-home/worker-home）与各 preset 的 `realHome`（`~/.claude`、`~/.pi/agent` 等）下也拒绝——这些文件常含网关 token。数据目录下的 `control-in|out`、`task-inbox|out`、`daemon.log` 同样拒绝；根目录本身是 junction 时按 realpath 后的位置比较。**和 `brain-presets.ts` 的 `credentialFiles`/`identityFiles` 有对齐测试**：新增 agent 凭据文件时测试会红。**硬链接是已知缺口**（realpath 无法区分 inode，已接受：提示注入本来就能让大脑自己读文件）。需要临时外发 `account.json` 这类文件时，登录者发 `允许敏感文件 [分钟]`（默认 2 分钟、上限 30，只在本 daemon 进程内生效、重启即失效）：**先开窗再发，或附件被拦下后回这条指令补发**都行（被拦下的路径在内存里保留 30 分钟，按用户隔离，最多 20 条）；窗口内**只跳过敏感名单**，UNC/网络路径、NTFS 数据流与大小上限照旧；每次放行在日志里注明「敏感文件已临时放行」。单文件默认 25MB（`WECHAT_OUTBOUND_FILE_MAX_MB`）。**别因为「允许任意绝对路径」就把 denylist 去掉**——那是提示注入偷 `account.json`/OAuth 凭据的最后一道闸。
- **入站媒体落盘位置与清理（2026-11-09；路径 2026-11-12 改为账号级）**：文件/视频/无转写语音在 `real`/`mirror` 存 `<账号>/media/inbound`、`sandbox` 才存 `<sandbox>/media/inbound`（prompt 同时给绝对路径）；文件名会过滤控制字符、Windows 非法字符与保留名（`CON`/`NUL` 等），同名自动加 `-1`/`-2`。启动时和每次写入入站媒体时（真正清理至少间隔 1 小时）按 `WECHAT_MEDIA_TTL_DAYS`（默认 30 天）与 `WECHAT_MEDIA_MAX_MB`（默认 1GB）清理，**只清这个目录**。有微信转写的语音不下载，**也不进 `attachments`**（转写就是文本；若仍算附件，语音版「结束任务」「继续」会被挡在快车道/任务续跑之外，还会误报「收到 1 个附件」）；无转写才下载，`silk-wasm` 解码失败就保留 `.silk` 并在 prompt 里说明——不要假装听懂了。
- **工具进度 item 11/12：微信客户端根本不渲染（2026-11-09 复核，默认关闭）**：官方 2.4.10 定义并发送 `TOOL_CALL_START=11` / `TOOL_CALL_RESULT=12`，但真机服务端只回 200/空响应、**不分配 `message_id`**，微信客户端不显示。`weixin-agent-sdk-rs`（2026-08-13 实测）穷举五种 wire 变体（`GENERATING`、与文本同一 `item_list`、补 `msg_id`/`update_time_ms`、去掉 `run_id`/`context_token`）均无变化，`getConfig` 也没有能力开关；galley（2026-10-10，官方 2.4.9）与 `dsh-wechat-bridge`（卡片默认关闭、长任务只发低频心跳）同样复现。`run_id` 只影响服务端关联，不影响客户端呈现。**所以 WeMind 默认发文本「步骤 N」**；`WECHAT_TOOL_PROGRESS_ITEMS=1` 可提前启用（代码已对齐 `FINISH` + 本回合 `run_id`，item 不计连发额度、也不顶替 5s 确认/15s 第二条（客户端看不到它）；item 发送失败回退的文本按可见消息补计一条额度，额度到线时干脆不发 item 以免回退文本挤占最后一条——此前用 `GENERATING` 不仅不显示，还让 3 条可见消息就误报「接近上限」）。等微信端开放后把默认改回开启即可。**start 与 end 成对处理**：start 每 15s 最多一条防刷屏，但 end 不受这个间隔约束；**end 只在工具耗时 ≥10s 时发**（短工具只留开始一条，避免每条命令刷两条消息、白占连发额度）；没发过 start 的工具不发 end（否则会出现编号对不上的「✅ 步骤 1」）。`emitProgress` 返回「是否真的发出」：额度用尽/等待「继续」时没发出，就不递增步骤号、不记 start，避免用户恢复后补一个从未出现过的编号。
- **「正在输入」续命间隔回到 5s（2026-11-10）**：客户端 typing 约 5–8s 自动过期。1.6.0 曾为规避「`getConfig`+`sendTyping` 网络抖动踩过期边界」把间隔从 5s 压到 3s，但请求量 +67% 且没有配置化，收益不足以抵消；现 `index.ts` 的 keepAlive 与 `task-manager.ts` 的每轮续命都改回 5s。**发消息本身会清掉 typing**，送达后立刻补一次（`sendWithTyping`），这条瞬时闪烁不可避免；要减少闪烁只能减少可见消息数。
- **引用只做内联（2026-11-09）**：`ref_msg` 的 `title` + `message_item` 直接拼成 `[引用消息] …` 前缀；只有 `svr_id` 时写「引用消息内容未缓存」，**不查本地缓存、不下载原消息**。要做完整引用（含图片/文件）需要另建消息缓存，当前明确不做（方案见 `待办与后续计划/待办-引用消息缓存.md`）。只引用、不输入正文时由 `contentlessNotice()` 回一条明确提示：不静默丢，也不拿空 prompt 问大脑（`askBrain` 的「用户发来一张图片」兜底会误导）。
- **带附件的消息不走快车道（2026-11-09）**：`isFastLane(text, tasks, attachmentCount)` 在 `attachmentCount > 0` 时一律返回 false。原因：控制/任务指令目前只消费文本，进快车道会把文件/语音/视频静默丢掉。代价是「任务：…」+附件会交给大脑而不是任务侧——这是有意的安全降级，要支持任务附件得先让 `injectTask` 能传本地路径。

- **real 模式下没有 `homeEnvVar` 的 Agent 会多拼一层路径（2026-11-12 修复）**：`claude-code` / `cline` / `qoder` 都用 `env` 把配置目录指到「沙箱根 + 子目录」（如 `CLAUDE_CONFIG_DIR=%HOME%/claude`），但 real 模式 `home` 就是真实 home，展开后会变成 `~/.claude/claude`、`~/.cline/cline`、`~/.qoder/qoder`。症状是 `Authentication required` 或首帧 60s 超时。修法是预设新增 `realEnv`（值为 `%HOME%`），只在 `home===realHome` 时按真实 home 展开；接入新的 `homeEnvVar` 为空、又用 `%HOME%` 模板的 Agent 时必须同时写 `realEnv`。
