### Added

- **统一输出出口 + 信息级别（2026-11-11）**：新增 `core/logging.ts`：`createLogger(scope)` 提供 `info/warn/error/debug` 四级（**DEBUG 预留**：当前无调用点，`WEMIND_LOG_LEVEL=debug` 才输出），格式 `[wemind/<scope>][LEVEL] …`，全部写 stderr（WARN 用 `console.warn`，其余 `console.error`）；`print()` 收敛 CLI 用户输出到 stdout，纯文本零前缀零级别。级别**写进文本而非分流管道**：watchdog 合并子进程 stdout/stderr 进同一个 `daemon.log`，分流会丢信息还会乱序，MCP 的 stdout 更是 JSON-RPC 通道。收敛 5 份自造 `log`/`dlog` 定义、17 处带前缀的裸 `console.error`、77 处裸 `console.log`；134 处运行日志逐条定级（INFO 73 / WARN 40 / ERROR 28 / DEBUG 0），**ACP 帧级关键线索（`spawn`/`initialized`/`session/new`/`prompt ok`）归 INFO 而非 DEBUG**，因为排障必须可见。`wemind log --errors` 改认 `[ERROR]/[WARN]` 标记，升级前旧日志按关键词兼容。`wemind version`/`help`/`list` 等用户输出零字节变化（CI 装包冒烟依赖）。守卫：`logging.test.ts`（5 条）、`cli-log.test.ts`（14 条）、`core-entry.test.mjs`。文档同步：AGENTS.md、README、docs/ai、已知坑、验收清单、代码地图、repowiki 04/06/07/08/09/10/11、两份 recipes、新手教程、速查、两个随包 README、llms.txt。
- **新增 `wemind log [key|label]`（2026-11-11）**：一条命令看该账号 `daemon.log` 的尾部。日志是**全量运行日志**（启动/消息轨迹/ACP 握手/发送进度/错误混在一起），默认最后 50 行保留上下文；`--lines N`（1..2000）、`--errors`（全文筛错误行再取尾部）、`--file N`（看轮转出去的 `daemon.log.N`，并列出其它轮转文件）。用 Node 自己读文件，跨平台一致；**刻意不做 `--follow`**：`RotatingLog` 靠 rename 轮转，跟随句柄会指向旧文件，实时看用 `tail -f <路径>` / `Get-Content -Wait`，pm2 路线用 `pm2 logs`。纯函数 `parseLogArgs` / `readLogTail` + 9 条单测（`cli-log.test.ts`）。命令表由 `docs:tables` 自动生成，文档同步：AGENTS.md §3、README.md、新手教程、速查、随包 README、llms.txt、验收清单、repowiki/11。

- **日志可观测性四项小修（2026-11-11）**：① `wemind log --errors` 不再靠泛正则：只认**带 `[wemind/...]` 前缀**且命中 `ERROR_MARKERS` 清单的行（清单含 `退避`/`限流`/`过期`/`挂起`/`接不上` 等不含 error 的项目文案），修「漏检异常、误捞正文里的 error」；每条命中**带前后各 2 行上下文**保留因果（`--lines` 仍按命中条数算），输出统计改为「命中 N 条错误，输出含上下文 M 行」。② 新增 `shared/io/repeat-log.ts`：`getUpdates error` 这类连续网络失败第 1 次照报、之后每 60 次带「连续 N 次」报一条、恢复时补一条 `recovered after N consecutive errors`，不再刷满 10MB 日志把线索顶进轮转文件。③ 启动行改 `[wemind/wechat-daemon] up. v<版本> bot=…`，贴日志时能看出跑的是哪版。④ 明确**不按 `console.error`/`console.log` 分级**：watchdog 把两条管道合并进同一个 `RotatingLog`、通道信息落盘即丢，且 70+ 个正常日志调用点也走 `console.error`，MCP 的 stdout 还是 JSON-RPC 通道——分级要全量改调用点还会破坏时间线，不划算。守卫：`cli-log.test.ts`（13 条，含真实错误文案样例与正文误伤反例）、`repeat-log.test.ts`（5 条）。

## [1.1.0] `@wemind/wechat-mcp` 补发已合入的修复（2026-11-06）

`@wemind/wechat-mcp` 停在 `1.0.5`（2026-10-27）期间，主分支合入了一批只影响 MCP 形态与内核的修复；这些条目**已记在下面 `[1.4.0]` 的 Fixed 段**（当时随 `@wemind/cli` 一起发布），但对 MCP 用户而言它们是**首次发布**。本次把 MCP 包版本提升到 `1.1.0`，让装了 `1.0.5` 的用户能通过 `npm i -g @wemind/wechat-mcp@latest` 拿到：

- **收消息按登录者白名单过滤**：`get_messages` 只返回登录者（或登录者白名单内）的消息，其它发件人被过滤。

- **传输错误分类与发送重试**：区分可重试与不可重试的传输错误。
- **登出失败不再谎称凭证已清除**。
- **登录登记 CLI 账号体系**：标准目录登录成功后自动登记 `accounts.json`，`wemind list` / `start` 可见；自定义 `WECHAT_DATA_DIR` 不登记。
- **重新扫码可并入现有账号**（会话过期重登不再要求手删账号目录）；高级登录态（验证码/IDC 重定向）立即失败并说明原因。
- **白名单与账号注册表的读-改-写加跨进程锁**（`file-lock.ts`，`wx` 锁文件 + 陈旧锁清理）。
- **POSIX 下凭证文件统一收紧为 600**；**图片下载边读边限流**，超限立即取消。

- **`daemon.log` 轮转与保留（2026-11-02）**：三个常驻 runner 原先都把 stdout/stderr 无限追加进账号目录的 `daemon.log`，崩溃循环（被 `WEMIND_MAX_RESTARTS` 拦下之前）或长期运行会把日志撑大且没有历史上限。新增 `log-rotate.ts`：`daemon.log` 达到 `WEMIND_LOG_MAX_MB`（默认 10MB）轮转为 `.1`（最新）… `.<WEMIND_LOG_KEEP>`（默认 3），`keep=0` 表示不留历史。builtin watchdog 改为把子进程 stdout/stderr 接成管道、由 `RotatingLog` 逐块追加——Windows 上不能改名仍被写入进程持有的文件，所以不能用继承 fd；这样运行中也能轮转，并且等 `close` 收完最后一块输出再写「daemon exited」。`run-daemon.ps1` 的 `*>>` 在子进程存活期间持有文件，只能在每次重拉前轮转。pm2 runner 的日志归 pm2 管理，文档要求装 `pm2-logrotate`。补 `log-rotate.test.ts` 与 README / 随包 README / 速查 / repowiki 08·09·10 / `daemon-常驻原理.md` / `AGENTS.md` / `docs/ai/README.md` 同步。
- **长大脑回合不再阻塞任务/控制指令（2026-11-02）**：消息原先只有一条 `msgQueue` + 一个串行 `workerLoop`——一条大脑回合最长可跑 15 分钟，期间发来的「结束任务」「任务列表」「#2 继续」乃至 `切换大脑` 都只能排在它后面（任务侧明明独立于大脑）。现在 poller 入队时按 `isFastLane()` 分拣：控制指令、任务指令、以及确实有可续跑任务的「继续」短句进 `fastQueue`，由新增的 `fastWorkerLoop` 与大脑回合并发处理；其余进 `msgQueue` 串行喂大脑。快车道命令之间保序；切脑/会话/交接仍要操作同一个 ACP 连接，会在 ACP 门口等当前回合结束（语义要求，不是排队阻塞）。出队时若「继续」短句已不再可续跑，交回大脑队列，保持旧语义。发送仍共用 `replyChain` 与连发额度；接近上限且本用户回合在跑时，快车道答复先让位，避免挤掉留给最终答案的最后一条。同步更新 repowiki 02/05/07、`docs/ai/README.md`、`AGENTS.md`，并补 `isFastLane` 分类单测。
- **Gemini 的 Google 登录凭据未同步进沙箱（2026-11-02）**：沙箱 `settings.json` 会原样镜像用户的 `security.auth.selectedType`，此前 `credentialFiles` 只有 `.env`。用 Google 账号登录（`oauth-personal`）的用户在沙箱里没有 token，Gemini 会在 ACP `initialize` 之前卡住登录流程——daemon 每条消息、每个 worker 任务、`wemind brain check` 都超时（API key 用户不受影响，所以本机实测发现不了）。现在 `credentialFiles` 增加 `oauth_creds.json` + `google_accounts.json`；账户切换/刷新走「新者胜」。
- **Gemini 的设置/MCP 目录按 JSONC 解析（2026-11-02）**：Gemini CLI 自己用 `strip-json-comments` 读 `settings.json`，允许注释；WeMind 的 `settingsBase`、MCP 目录、`wemind brain check` 却用严格 `JSON.parse`，带注释的合法配置会被静默当成损坏——沙箱丢失 `model` / `security`，`加载 <MCP>` 报「未找到」。三处统一改用 `parseJsonc`，并加带注释设置的沙箱用例。
- **无编号消息默认归大脑，任务追问改为显式寻址（2026-11-02）**：此前只要有一条 `waiting` 任务，任何无前缀消息都会被它接管——任务早已出完结果、用户想找大脑聊天时，消息会被静默吞掉（真机两次：#26、#28）。现在 `task-manager.shouldResumeTask()` 只放行「继续 / 接着跑 / continue」这类短句，且必须存在可续跑任务（有 waiting；或没有活跃任务时存在 interrupted——多条时任务侧回编号清单让你指明）；其余一律走大脑。任务追问用 `#<编号> 正文`（新增全角冒号容错 `#2：正文`；半角冒号留给时间 `#1:30`）、`> 正文`（明确发给任务的短前缀；无任务时新开一条）、`任务 …`。每条任务结果/中断推送末尾附一行 `↩ 回这条任务用「#2 正文」；不带前缀的消息会交给大脑。`。同步更新路由、任务推送文案、测试与文档（README / 新手教程 / 使用指南 / repowiki 07 / AGENTS / docs/ai）。**真机验证（2026-11-02）**：任务 #29 停在 waiting 后，无前缀「只回复数字 7」走大脑（回复 7），`#29 只回复数字 8` 进任务（`prompt ok 1193ms`），任务推送挂起补发正常。
- **pi 的启动横幅不再混进回复（2026-11-01 真机）**：pi-acp 把 pi 的启动信息（`## Context` / `## Skills` …）当作 `agent_message_chunk` 发给客户端（给 Zed 之类看的启动面板），微信里就成了每条新会话首答的前缀。预设新增 `settingsDefaults` 字段（只补沙箱 `settings.json` 里缺失的键，用户显式设过就保留用户的值，真实配置不动）；pi 用 `settingsDefaults: { quietStartup: true }`（pi 官方 settings.md 的开关）关掉。
- **worker 沙箱按任务 agent 准备（2026-11-01 真机）**：daemon 启动时只按默认任务大脑备一次 `worker-home`；派发到别的 agent（`wemind task --agent pi` / 微信「任务 pi：…」）时它自己的 `settings.json` / `models.json` / 凭据还没进沙箱，pi 会拿空配置跑（任务输出异常）。现在 `worker-pool.ts` 的 `acquire` 在复用/起进程前按**这条任务的 agent** 调 `ensureWorkerHome(ag)`。
- **MCP 登录接入 CLI 账号体系（2026-11-02）**：MCP 形态原先只把凭证写进 `DATA_DIR`，从不登记 `accounts.json`——用 `login_qrcode` 登录后，`wemind list` / `wemind start` 完全看不到这个账号；遇到需要验证码/IDC 重定向时又只提示可能没安装的 `wemind login`。现在：标准目录（`DATA_DIR === accountDir(ACCOUNT_KEY)`，默认 `~/.wemind/default` 且未设 `WECHAT_DATA_DIR`）登录成功后自动登记（key = 目录名，默认 `default`），`logout` 在核对 botId 后注销条目；自定义 `WECHAT_DATA_DIR` 不登记（注册表只能指向 `accountDir(key)`）。相关提示与工具描述补上 `npx -y @wemind/cli login` 兜底。补 MCP 登录/登出的登记与不登记用例。
- **发布保障对齐两个包（2026-11-02）**：`wechat-mcp` 此前只有 `npm pack --dry-run`，没有 `prepack` 守卫、发布不带显式 provenance、也没有装包冒烟——空壳包/打包回归要到真正 publish 时才发现。现在补 `prepack: node scripts/prepack-guard.mjs`（与 CLI 同一份守卫），发布命令加 `--provenance`，发布前把 tarball 真装到临时目录、用临时 `WECHAT_DATA_DIR` 走一次 MCP `initialize` 握手并断言 `serverInfo.name=wemind`。同时把 `check:version` 与两个包的 `npm pack --dry-run` 加进 `npm run verify` 和 CI（版本/打包问题在普通 CI 就暴露，不必等到发布工作流）。

- **发图 URL 增加 SSRF 防护（2026-11-02）**：`resolveImageBytes` 原先直接 `fetch` 大脑回复里的任意 http(s) 链接——微信消息里的提示注入可以诱导大脑输出 `http://127.0.0.1:…` 或内网服务地址，daemon 会把内网响应当图片发回微信。新增 `image-url.ts` 的 `assertPublicHttpUrl`：只允许 http(s)，拒绝回环/私网/CGNAT/链路本地（含云元数据 `169.254.169.254`）/组播/保留地址以及 IPv6 与 `::ffff:` 映射形式；域名先解析并逐个地址检查（解析失败也拒绝）。重定向改为手动跟随、**逐跳复查**、最多 3 跳（原先 `fetch` 自动跟随可绕过第一跳校验）。本地文件绝对路径不受影响。补 `image-url.test.ts`（地址分类与 DNS 结果）和「重定向到内网」「超过 3 跳」用例。

## [1.2.0] 运行时切换大脑 · 多 worker 进程池 · 完整会话管理（2026-10-30）

### Added

- **运行时换对话大脑（微信 + CLI，不再重启 daemon）（2026-10-28）**：此前换大脑只能 `wemind brain set X --restart`——重启整个 daemon、打断在途任务、丢在途回合。现在微信 `切换大脑 [名]` / `AI 大脑 [名]` / `/brain` / `/ai brain`，CLI `wemind brain switch <agent 名|auto>`，**在同一个 daemon 进程里**换：预检（未知/不可用 agent 直接拒绝，不 spawn）→ `drain` 等在跑的回合结束（默认 30s，`WEMIND_SWITCH_DRAIN_MS`）→ 准备新沙箱 → `restart` + `initialize` 启动新大脑（硬上限 `WEMIND_SWITCH_TIMEOUT_MS` 默认 120s）→ **成功才写 `brain.json`**。失败**回滚**：槽位留旧大脑、清掉半截 pid 记录、回一句「已回滚到 X，下一条消息会自动重启它，不用手动处理」；持久化放最后，所以回滚无需撤销。同一目标的并发请求复用同一次切换（启动新大脑只做一遍）、切另一个目标直接拒绝（不排队，避免「连点两下」的歧义）。切换期间到达的用户消息会在 ACP 门口等新大脑就绪（有界等待，全程只 spawn 一次）。**`WEMIND_BRAIN` 陷阱**：环境变量优先级高于 `brain.json`，命令式切换绕开 env 生效，答复里会警告「重启后会回到环境变量指的大脑」。新增 `brain-switch.ts`、`acp-brain.ts` 的 `isTurnInFlight/beginSwitch/drainTurn/warmup` 与 `askBrain`→`runTurn` 拆分。
- **多任务 / 多 agent 并行：worker 进程池（2026-10-28）**：任务侧此前是**单任务单进程**（`activeTask` + 模块级 `child`/`taskSessions`/`pendingCwd`），做不到「a 大脑做任务 1、b 大脑做任务 2」。现在每条任务一条独立 ACP 连接（`worker-acp.ts` 从模块单例重写为 `class WorkerConn`，`worker-pool.ts` 管复用/回收）：
  - **派发时指定 agent**：微信 `任务 <agent 名>：正文`（冒号前必须是**已知 agent 名**才算指定；不是 agent 名时——如 `任务 明天：去买菜`——不当成指定 agent，整句仍是派给任务侧的正文）、CLI `wemind task "…" --agent <名字>`；不指定则用**默认任务大脑**（`worker.agent ?? agent`）。
  - **默认任务大脑（本次运行内一直生效）**：微信 `切换任务大脑 [名]` / `/ai task`、CLI `wemind brain switch <agent 名> --worker`；**不写 `brain.json`**（重启回到配置值，答复写明），有任务在跑且与目标 agent 不一致时重启空闲进程。
  - **编号寻址**：任务编号按用户**单调递增、不复用**（避免「任务 2」在对话里指代变化），跨重启不归零；`#<编号> 正文` / `wemind task-reply <编号>` 发给指定任务；只有一条任务时免编号（延续「回一句话就继续」的顺手）。
  - **池**：进程常驻复用 + 空闲回收（并发上限 `WEMIND_MAX_WORKERS=3`、空闲进程上限 `WEMIND_IDLE_MAX=2`、空闲超 `WEMIND_WORKER_REAP_MS=5min` 回收）；取用顺序是「同 agent 空闲命中 → 回收最旧空闲腾位 → spawn」；`wemind stop` 一次杀光池里全部 worker（`workers.pid.json` 记录数组）。
  - **任务列表**：微信 `任务列表` / `/tasks`、CLI `wemind task-list`（编号/agent/状态/轮次/已运行/最近输出），`结束任务 [编号]`、`结束全部任务`。

- **CLI 控制桥：让 CLI 与微信走同一段代码（2026-10-28）**：切换大脑/开新会话/恢复会话都必须发生在 daemon 进程里（进程内的 ACP 连接、会话当前会话记录、任务表都是它的活状态）；CLI 另起进程改文件只能改「下次启动才读」的配置。新增 `control-bridge.ts`：CLI 原子写 `control-inbox/<ts>-<id>.json`，daemon 定期扫描执行并写 `control-out/<id>.json` 应答，CLI 短轮询打印——`wemind session {list,new,resume,rename,delete}`、`wemind brain switch|handoff`、`wemind task-list/task-reply/task-stop` 走桥，微信侧与 CLI 侧复用同一实现。**升级期可用性**：`control-out/.bridge` 记着 daemon 自己的 pid，pid 对不上就说明它在跑旧版本——写命令在**发出前**就拒绝并给出「重启一次」的命令（把 30s～165s 的静默等待换成一句能照做的话），`list`/`rename`/`delete`/`task-list` 则**降级**成直接读文件 + 一行说明（离线也能用，只是按「下次会用的那个大脑」列）。**安全边界**：桥只接受**agent 名与纯数据**（target/ref/name/text/id/page），**没有 bin/args/shell 的位置**——就算被伪造（进程本就能写账号目录，task-inbox 同性质），最坏也只是「选一个已装的 agent 或清掉自己的会话」。
- **帮助总览与 `/ai` 家族（2026-10-28）**：微信 `帮助` / `/help`、CLI `wemind help`（与微信**同表**，CLI 不列只在微信里存在的 MCP 加载/卸载），按角色裁剪（非 owner 看不到 owner-only 命令）。新增 `/ai` 家族前缀：`/ai`（列可选 agent + 当前对话大脑/默认任务大脑）、`/ai brain [名]`、`/ai task [名]`；中文（`切换大脑`、`切换任务大脑`）与旧斜杠（`/brain`、`/worker`）保留为等价别名。**非 owner 发 owner-only 命令 → 短提示拒绝，不转发给大脑**（也不再让大脑「意外回答」这类命令）。

- **任务桥补回结果通道：CLI 不再自己编「已派发」（2026-10-29）**：`wemind task/task-reply/task-stop` 此前只把命令丢进 `task-inbox/` 就返回，只能靠轮询 `task-state.json` 的 `active` 猜结果。现在命令文件带一个答复编号（`ack` 字段），daemon 处理完把**真实结果**写 `task-out/<id>.json`（新增 `task-inbox.ts`，两侧共用；`setTaskAckSink` 依赖注入，与 `setTaskPush`/`setTaskStateSink` 同款），CLI 短轮询后打印 daemon 的那句话。**派发的答复延迟到 `acquire` 之后**（达上限/agent 起不来是那时才知道的，`Task.ackId` 带到 `runTask`），所以「已派发任务 #3（kiro）」是真话；**空文案也是一种答复**（＝「已送达、无别的话」），CLI 据此立刻用自己的措辞、不干等超时；等不到答复（老版 daemon 不认这条通道）才退回「已发送…」**并附一句说明**，不把「没等到」当成功。CLI 等派发答复最多 30s（冷启动可能几十秒）、等回复/结束 5s。

### Changed

- **权限措辞纠正：只有「登录者」，没有「主号」（2026-10-29）**：平台事实是**必须扫码登录该 bot 才能给它发消息**，所以每个 bot 只有它的**登录者**（扫码登录它的那个微信号）能发——此前的「账号本人（owner）/ 已授权用户」写法容易被读成「多个微信账号之间有一个主号」，已全仓库统一为「**登录者**」与「**登录者白名单**（`allowFrom`，默认拒绝；**兜底校验**，防发送范围将来变化 / daemon 被接到别的入口）」，作用范围写成「**整个账号（仅登录者）** / **登录者的会话** / **登录者的任务**」；`allowlist`/`allow`/`revoke` 明确为兜底工具（正常无需碰）。文档与示例里的 `--label 主号` 一律换成 **`--label 工作号`**，并注明 **`label` 只是别名（昵称）、与权限无关**、「主号 / 主账号」列入**禁用措辞**。另在 README「多账号管理」与 `repowiki/06` 新增**多账号下换大脑的范围、限制、两个入口（微信 / 本机 CLI）的区别**：作用对象（消息进来的那个账号 vs 可指定任意账号）、谁能做（仅登录者 vs 本机机主）、daemon 在跑/没跑时的行为（热切换 vs 只写 `brain.json`；`--worker` 必须先有 daemon）、写入磁盘的时机（都成功才写）、没有跨账号批量、控制桥只收 agent 名。
- **模型/账号侧出错的任务不再抢消息（2026-10-29）**：一条任务若一轮失败在 provider 那类错误上（余额/额度不足、密钥鉴权、计费、模型不存在），它会**直接转「已中断」**而不是照旧停在「等你回复」。原因是「等你回复」的状态会抢下一条无编号消息（「谁在等就喂谁」）——真机踩过：一条余额不足的任务把用户之后的「在吗」吞掉，只是又白失败一轮，日常对话也断了。`interrupted` 不在 liveTasks 里，路由自然放它走；用户把账号修好后回「继续」/`#n 继续` 才续跑（两个入口不同路：无编号的「继续」这类整句短句走关键字闸 `looksLikeResume()`，`#n 继续` 在解析层就被 `#<编号> 正文` 分流）。判据是 `task-manager.ts` 的 `providerIssue()` 关键字表（错误措辞来自各 agent 的 provider、不统一），**认不出的一律按老规矩停在「等你回复」**（宁可多抢一次，也不把偶发失败误判成账号问题）；**限流（429/rate limit/overloaded）优先不归类**（等一会儿重试就会好，仍走老路）——Google 的按分钟 429 原文是「Quota exceeded for quota metric … requests per minute」，只按关键字会把限流误判成额度问题；续跑前缀文案改成中性（原先写死「daemon 重启时中断了」，provider 场景不准确），并统一提示「先核对上一步是否已产生副作用」；续跑期间**起不来**（agent 不可用/池满）不再删掉任务记录（原先无条件删，等于把「修好后回继续」这句承诺作废）；「接不上」的文案不再劝「把进展重述一遍」（重述走的还是同一条恢复路径），改为指出重试是同一结果、要重来就结束这条任务后重新派。
- **`任务 <agent 名>：正文` 不再顺带改「默认任务大脑」（2026-10-29）**：此前微信发 `任务 kiro：…` 除了派这条任务，还会**顺手把进程内的默认任务大脑也改成 kiro**（不写入磁盘、答复里也不提示）。它既是**账号级**副作用（`切换任务大脑` 因此是 owner-only）却对所有发件人开放，又与本机 CLI 的 `wemind task --agent`（从来没有这个副作用）不对称。现在指定 agent **只对这条任务生效**；要改默认任务大脑只能用微信 `切换任务大脑`（owner-only）/ CLI `wemind brain switch <agent 名> --worker`，两个入口口径一致。
- **`wemind start` / `stop` 可省略账号（2026-10-29）**：不带 `<key|label>` 时用**默认账号**，与 `session`/`task*` 的口径一致（同一套 `pickKey()`）；`stop` 的答复现在带解析到的账号（`账号 <key>：已停止 …`），省略写法下不会「静默换目标」。默认账号就是 `accounts.json` 的 `default`：**首个登记的账号自动成为默认**，`default` 字段缺失（老注册表）时回落第一个账号，删掉默认账号自动轮到下一个；`wemind list` 标 `[默认]`、`wemind set-default <key|label>` 可改。注意 **label（别名，给人看）与 default（省略账号时用哪个）是两个字段**：`wemind label <key|label> <新别名>` 只改前者。`logout`/`delete` 等破坏性命令仍必须显式指定账号。
- **`wemind brain set` 不再整体覆盖 `brain.json`（2026-10-28）**：改为读-改-写（原先整体覆盖，新增的 `worker` 段会被抹掉），并新增 **`presets` 段**——按 agent 名保存启动覆盖（`--bin`/`--args`/`--shell`/`homeEnvVar`），换 agent 时把旧顶层覆盖迁移进去：否则「切走再切回」会丢 DSH 的 `--bin <绝对路径>`。同一 agent 再次 `set` 时沿用未给出的字段。`brain set <agent 名>` 现在在 daemon 在跑且**认控制桥**时**当场应用（不用重启）**（走控制桥，等于 `brain switch`：先启动新大脑、成功才写入磁盘，失败退回）；带 `--bin`/`--args`/`--shell`/`--model` 时只写入磁盘（桥不接受这些字段）——其中 `--bin`/`--args`/`--model` 随后用同名 `brain switch` 可当场应用，`--shell` 要重启；daemon 没跑/跑的是不认桥的旧版时同理（答复写明）。
- **大脑侧认得出 provider 的永久错误：不再白重试 3 次（2026-10-29）**：agent（如 DSH）把 provider 的回合失败统一包成 `-32603 … turn failed: …`，只按错误码看会归进「后端瞬时错误」——于是余额不足这类**修好之前永远失败**的错误也被重试 3 次，而每次重试都要先冷启动一个 agent 进程，最后给用户的建议还是「稍后把消息再发一次」。现在 `index.ts` 的 `brainFailurePlan()` 复用任务侧同一张 `providerIssue()` 关键字表：额度/余额不足、密钥鉴权、计费、模型不存在 → **只试 1 次**，回复改成说清原因（「（这次没答上来：额度/余额不足。这类问题重试不会好——把账号/模型处理好后，把消息再发一次就行）」）；**限流/瞬时错误仍按 backend 重试**（关键字表限流优先，顺序别改）。日志 `brain error (try 1, provider：额度/余额不足)`。
- **DSH 默认模型：跟着你自己的 profile 走，WeMind 不代改配置（2026-10-29）**：根因——`dsh --profile acp` 的 ACP 桥插件（`@deepseek-ai/dsh-acp`）默认模型写死在它**自己的 bundle patch** 里（`app.asar` 内 `@deepseek-ai/dsh-acp-app/cordis.patch.yml` 的 `- id: acp` → `deepseek-official/deepseek-v4-flash`，该路由要 `DEEPSEEK_API_KEY`，一 prompt 就 `no API key`），而 profile 用户层只覆盖 `llm-pi-ai` / `agent-default-model` / `web-search-deepseek`——`- id: acp` 得**用户自己**补（插件 README 原话：a later patch can replace that row's complete config）。按「用 agent、不改造它」的约束，WeMind 只做两件事：① 两个沙箱把真实 `profiles/acp/cordis.patch.yml` **原样复制**（`syncProfilePatch`，不追加任何条目；不然沙箱里那份是首次启动生成的空壳 `[]`，连 magpie 路由都不存在）；② 缺 `- id: acp` 时，`wemind brain` 直接给出一段可粘贴的 YAML（值取自 `agent-default-model`），让用户补到**真实 profile**——补完终端 dsh 与微信大脑才是同一个模型。默认模型由 `profile-model.ts` 读（**优先 `- id: acp`，否则 `agent-default-model`**），会话建立后按它发一次 `session/set_config_option`（agent 自己的 ACP 接口；幂等，显式 `--model` 覆盖走它）；桌面端改模型后，下次启动 daemon 或 `wemind brain switch deepseek` 时跟着改；`--model auto`/`default` = 跟随真实 profile 的默认（读不到就不下发）；完全没写 model 且读不到才回退 `deepseek-account/deepseek-flash`。**防回环不放松**：profile 复制进沙箱前会剔除用户自己挂的微信 MCP 条目（跑 `wemind-mcp` 的、或 `serverName: wechat` 的 mcp-client，`stripWechatMcpEntries`；真实文件不动、日志告警），其余条目原样保留。实测（`0.2.1-rc.3`）：真实 profile 里有 `- id: acp` 时，沙箱副本同样带它，`session/new` 的 currentValue 直接是 `["magpie","auto/deepseek-v4.1-flash"]`、prompt 正常答出、`resume` 后保持；走 magpie **不需要 API key、也没有余额错误**——前提是桌面端（DeepSeek Harness）在运行（magpie 是本机网关 `127.0.0.1:3425`，与日常 dsh 用 magpie 的前提相同）。
- **模型不再写死在 agent 预设里（2026-10-29）**：DSH 的 `model` 此前只能改 `brain-agents.ts` 常量再重建。现在可用 `wemind brain set <agent 名> --model '…'`（写进 `brain.json` 的 `presets.<agent>.model`，顶层同步一份供旧版 CLI 读；也可以是顶层/`worker` 段的 `model`）覆盖，解析优先级「本段 > `presets[agent 名]` > 真实 profile 的默认 > 预设兜底」；`--model auto`（或 `default`）= 跟随真实 profile 的默认。`wemind brain` 的「生效」行显示 `model=`。`--model` 与 `--bin` 同档不走控制桥（只写入磁盘），但 daemon 在跑时可用 `wemind brain switch <同名 agent>` 当场应用（模型已纳入 `sameAgent()` 的判据）；否则重启 daemon 生效。实测背景（`scripts/acp-probe.mjs`，DSH `0.2.1-rc.3`）：`session/new` 的默认模型是 `deepseek-official/deepseek-v4-flash`、需要 `DEEPSEEK_API_KEY`（原因见上一条：桥插件 bundle patch 写死 `- id: acp`），而桌面登录/桌面网关对应 `deepseek-account/*` 与 `magpie/*`（后者见上一条）。
- **agent 不再在进程启动时冻结（2026-10-28）**：`acp-brain.ts`/`mcp-sandbox.ts`/`worker-acp.ts`/`worker-sandbox.ts` 里的模块级 agent 常量与沙箱路径常量全部下沉——新增 `agent-slot.ts`（懒解析 + 记忆化 + `seedSlots` 启动种入），brain 与 worker 的每个过程显式接收 `ag`（入口取一次、过程内不再读槽位，握手中途换 agent 因此不可能发生），沙箱路径改私有函数，`firstFrameMs`/心跳改为**每回合现算**（此前 import 期定死，切到 DSH 会继续用旧心跳）。顺手修掉一个真 bug：`agentConfigFor(worker)` 原本丢掉顶层 `presets`，导致「有 `worker.agent` 时 `presets[agent]` 查不到」、`--bin` 之类覆盖对 worker 静默失效。
- **进程身份从「按配置猜」改为「按起进程时的记录」（2026-10-28）**：`manage.ts` 过去用**配置里**的 agent 算进程特征串，三种场景会失效：`brain set X` 不带 `--restart`、热切换窗口内、以及多任务/多 agent 并存（多 worker 之后这是常态）。现在 `brain.pid` 是 JSON 身份记录、worker 是 `workers.pid.json` **记录数组**（各含起进程时真实用的 bin/args/state/taskId），`manage.ts` 直接按记录算特征串与展示 live 状态，缺失时回退配置（兼容旧账号）；旧版 CLI 读新文件会拿到 `NaN` → 显示「已停止」且**不杀**（安全侧）。`task-state.json` 增补 `tasks` 数组并让顶层字段复制最近一条，旧版 CLI 读到仍能显示、不会误判成「无任务」。
- **`session-registry.json` 与任务表不并进既有文件（2026-10-28）**：`brain-sessions.json` 在关键路径（`ensureSession` → `session/load`）且已背了一层旧格式迁移，值是 string→object 要再迁一次还会波及 worker 孪生代码；所以会话登记表、任务表各自独立成文件，读失败一律降级（表→空、列表不可见）只记日志。写入一律 tmp + rename。

### Fixed

- **用相对路径手跑 CLI 时「daemon 明明活着却说未运行」（2026-10-28）**：`CLI_PID_MARKERS` 只有 `["wemind","cli.js"]`——`node packages/wechat-daemon/dist/cli.js daemon`（正是 `AGENTS.md` §3 教的写法，在仓库根直接跑）的命令行里既没有仓库名也没有包名，`isOurProcess()` 判否：`wemind list` 显示已停止、控制桥一律拒绝发送。追加一组 `["wechat-daemon","dist","cli.js"]`（要求 `dist` 同在，减少误判——这串最终用于**杀进程**），单测补相对/绝对路径与反例。
- **`wemind brain set X` 不带 `--restart` 时 `list`/`stop` 用错特征串（2026-10-28）**：进程特征串按**配置里**的 agent 算，配置已改而旧 agent 的进程还在跑时，`list` 显示「已停止」、`stop` 直接跳过（不杀）；多 agent 并存时更必然错。改按 `brain.pid`/`workers.pid.json` 记录里起进程时真实用的 bin/args 算（见上方「进程身份」条）。
- **`wemind task-stop`/`stop` 与改成进程池后的 worker 对齐（2026-10-28）**：`stop` 过去只杀单个 `worker.pid`，现在一次杀光 `workers.pid.json` 里全部记录（兼容旧的裸整数文件）；结束**在等回复**的任务时进程**留着复用**（不再杀），结束**正在跑**的那条仍只能力杀（ACP 回合没法优雅取消），空闲回收交给池。
- **`wemind task` 报「已派发」但任务被拒（2026-10-29）**：端到端验收暴露的假成功——达上限被拒时它会打印「已派发任务 #2（opencode）」（**上一条**任务的编号，因为 `task-state.json` 的 `active` 本来就是 true），`task-reply 9 "…"` 无论有没有 9 号任务都打印「已发送给任务 #9」，「结束任务 9」同理。原因是答复全靠 CLI 猜（见上方 Added 的回结果通道）。顺带修掉同类的第二次假成功：`resumeTask` 的「接不上（原 agent 现在用不了）」原先只 `push` 给微信、`return ""`，CLI 会报「已发送」——现在改成返回值（微信侧照旧收到一条 notice，CLI 侧拿到真话）。
- **从 VS Code 集成终端 `wemind start` 会「假启动」（2026-10-29）**：VS Code「智能自动附加」注入的 `NODE_OPTIONS=--require …/ms-vscode.js-debug/bootloader.js` + `VSCODE_INSPECTOR_OPTIONS`（`deferredMode`）会让**脱离式的后台守护进程**等调试器等不到、一行 JS 不跑——答复打印「已启动」，实际 `daemon.log`/`wrapper.pid` 不更新、daemon 没起（前台命令因为被调试器接上，`stop`/`list` 都正常，极难察觉）。现在 `watchdog-runner.ts` 在启动后台守护进程与它拉起 daemon 前都用 `debug-env.ts` 的 `stripVscodeDebugEnv()` 摘掉这段注入（只摘 VS Code 那条 `--require`，用户其它 `NODE_OPTIONS` 保留；补 7 个单测）。
- **daemon 重启后回无编号「继续」其实没去续跑（2026-10-28）**：任务表的路由顺序（唯一在等的那条 → 唯一在跑的那条 → 0 条在跑且 1 条「已中断」则续跑）写在 `injectTask` 里，但微信侧的无前缀入口闸只放 `waiting` 的任务进去——于是重启提示说的「回『继续』可续跑」在微信里落空（CLI 的 `task-reply 继续` 不经过此闸，反而走得通）。现在补一层关键字闸 `looksLikeResume()`：**没有活跃任务 + 存在「已中断」任务 + 消息就是「继续 / 接着跑 / continue」这类短句**才放行进任务表；其余消息照常走大脑——不设这层闸的话，一条陈旧的中断任务会把之后的日常提问全吞掉。补单测（关键字正/负例 + 无编号续跑真的拉起进程并 `strictResume`）。

- **daemon 重启后、用户下一条消息前的外发全部丢失（2026-10-29）**：`state.contextTokens` 在重启后还是上次运行留下的 `context_token`，服务端不认；新 token 只有该用户发来下一条消息时才会到。这段时间里任务结果（`setTaskPush`）与 CLI 指令答复（`sendNotice`）一律 `ret=-2 (prepare failed)`，`reply()` 内部重试仍是同一个旧 token，错误又被 `sendOrdered` 吞掉 → 消息**静默丢失**（真机复现：跑完的任务只在 `任务列表` 里看得到，微信一条都没收到）。现在这类「必须送达」的外发**只在该用户本进程还没发过消息时**失败才挂起（新 `pending-push.ts`：每人上限 20 条、超出丢最旧、只在内存；本进程收到过该用户的消息之后，`-2` 当限流处理、不再挂起——免得把过时答复拖到下一条消息），等该用户下一条消息带来新 token 后按原顺序补发：这一批消息的计数重置全部做完后再补（每个发件人一次，否则同批后一条消息的 reset 会把补发计数抹掉）、排在该批消息触发的进度/答案之前、计入连发额度、每轮最多 5 条且不越过本回合留给答复的额度（剩下的留给后续消息）。另外重置计数改为「按还没发完的条数计」（`inflightSends`）而不是直接清零——已经排队、会在本条消息之后才上线路的发送仍占服务端额度，不这样就可能把最终答案挤到限流上。补发失败（任何原因）就重新挂起，同一条最多补发 3 次，超过就放弃并记日志。`sendOrdered` 新增可选 `onError`，回合内的普通回复（进度/答案）不走挂起。daemon 再重启一次挂起队列会丢——任务结果仍能在 `tasks.json`/`任务列表` 里看到，用户发一条消息后由「继续」续跑。

- **改了模型再 `brain switch` 会谎报「无需切换」（2026-10-29）**：`brain-switch.ts` 的 `sameAgent()` 只比 name/bin/args，模型差异被判成「已经是它」→ `switchBrain` 直接回「当前对话大脑已经是「X」，无需切换。」，既不重启 ACP 子进程也不 `setAgent`——运行中的大脑一直用旧模型，而磁盘与 `wemind brain` 的「生效」行已经显示新值。现在 `sameAgent()` 把 `model` 纳入判据（name/bin/args/model）：模型变了就是一次真切换（restart → `session/load` → 重新下发 `session/set_config_option`）；`index.ts` 的 `setTaskBrain`（微信 `切换任务大脑`）也用同一组判据（顺带补上此前漏比的 `args`），但它的「切换」是换 worker 槽位 + 回收空闲连接——在跑/等回复的任务仍用旧 agent 跑完，**之后的新任务**建连时才下发 `session/set_config_option`。
- **`brain set` 的参数解析三处漏网（2026-10-29）**：① `--model=VALUE` 等号写法整 token 匹配不到、被当未知开关**静默丢掉**而命令仍报成功——`takeFlag` 现在两种写法都认；② 未知开关（如拼错的 `--modle`）一律静默过滤——现在直接报错；③ 空 `--model`（`--model ""` / `--model=`）什么都不写却把命令切进「需重启」分支——现在报「缺少参数值」（要清空/跟随默认请写 `--model auto`）。另外 `brain set auto --model …` 的模型会被写进**永不读取**的 `presets.auto`（解析时 `auto` 换成探测到的具体 agent），而顶层那份却会作为「本段覆盖」下发给探测出来的**任意** agent——现在 `brain set auto` 带 `--model` 直接拒绝，提示指定具体 agent。
- **provider 错误的提示对「密钥/模型」两类是死路（2026-10-29）**：`brainErrorMessage` 原先一律说「把账号/模型处理好后，把消息再发一次就行」——但运行中的 daemon 不重读 `brain.json`、也不重新同步凭据（槽位启动时种入），照做仍然失败。现在「密钥/鉴权有问题」「模型不可用」两类额外提示「刚改过登录态或模型配置的，还要重启一次 daemon（`wemind stop && wemind start`）才会读到」；余额/计费不改（provider 侧充值后重发即可）。
- **`brain check` 在坏 profile 上假绿、缺条目的提示会教出非法 YAML、flow 式 `- id: acp` 被忽略（2026-10-29）**：① `wemind brain check` 的临时 home 原先不复制 `profiles/<名>/cordis.patch.yml`，而 daemon 的沙箱会复制——profile 写坏时自检仍报 ✅，daemon 却每条消息都起不来（DSH 启动即解析该文件，语法错直接 exit 1）。现在自检同样复制（并同样剔除微信 MCP），失败详情保留首行 `Error`（「failed to parse overlay … YAMLException」）而不是只剩栈尾。② profile 还是空壳 `[]` 时，`wemind brain` 对缺 `- id: acp` 的提示原先教「加到文件末尾」——`[]` 是已写完的 flow 根节点，后面再接块序列项是非法 YAML（实测 dsh 直接 `exit 1`）；现在提示「把 `[]` 那一行替换成这段」，读不到默认模型时给 `<provider>`/`<model>` 占位并说明怎么换。③ 用户把 `- id: acp` 写成 flow 式（`config: {provider: magpie, model: auto/x}`）时，读默认模型的定点解析原先不认，会拿 `agent-default-model` 的值覆盖用户显式选择；现在块式与 flow 式都认。

### Fixed
